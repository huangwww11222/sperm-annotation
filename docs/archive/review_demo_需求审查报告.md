# review_demo.html 需求与交互审查报告

审查日期：2026-09-26  
审查对象：`review_demo.html`（1149 行，原文件未修改）  
依据：`审查模式_功能交互说明.md` v1.1  
方法：源码审查、Chrome 浏览器鼠标和键盘实测、1600×1000 与 1366×768 视口检查。

## 1. 结论与评估范围

该 demo 已表达六区布局和 B 审查的主要操作入口，但尚未满足完整功能交互要求。当前适合讨论布局、信息组织及初步操作，不能作为审查流程已经正确实现的验收样例。

主要差距集中在编辑正确性、保存恢复、帧提交计数、视频状态和完成后的版本保护。部分功能有提示或按钮，却没有对应行为。

这是前端原型，不要求现在部署生产后端；但要验证自动保存、断点续审和最终版本等交互，至少需要可恢复的本地数据或明确的模拟状态。没有后端本身不是缺陷，把未实际保存的数据显示为「草稿已保存」、把未生成的版本显示为「已固定审查版本 B」则会误导评审。

原型图片没有作为本次可读取附件提供，因此本报告不评价与图片的像素级一致性。v1.1 中新增快捷键映射、重新编辑规则和 C 具体完成动作属于文档标明的实施建议，与原对话明确的核心规则分开评价。

所有浏览器操作都在独立测试会话进行；文件未改动。视频完成入口测试将浏览器内的任务临时缩为 1 帧以覆盖末帧场景，不代表完成了真实的 1000 帧审查。

## 3. 需要优先修复的问题

优先级说明：P1 会丢失修改、破坏状态或阻碍核心审查；P2 影响操作一致性、可见性和可用性；P3 为次要提示与显示问题。

### R01 · P1 · 自动保存和断点恢复未真正实现

**证据：** `endDrag()` 第 816～825 行、`undo()` 第 913～922 行只是延迟 400ms 后修改提示；没有持久化写入。第 657～677 行在每次加载页面时重新随机生成 A/B 框。

**实测：** 编辑之后等待保存提示，再刷新页面，修改消失，连 A 的几何也重新生成。所谓「草稿已保存」不能支撑关闭重进。

**同时缺失：** 没有逐帧草稿实体、更新时间、继续编辑/放弃修改选择，`draftSaved` 是全局布尔值。旧帧的保存定时器也能在新帧上显示成功信息。提交后自动跳到 pending 帧，保存栏还显示「本帧已提交」，没有当前帧状态标签纠正这一歧义。

**建议：** 原型阶段使用固定数据集，并通过 IndexedDB 或适量 localStorage 数据保存任务状态、A 基准、草稿和帧提交。为保存结果绑定视频、帧和版本；逐帧显示保存状态及审查状态，真正失败时提供重试。生产版再接入服务端契约。

### R02 · P1 · 重复提交修改帧会重复计数

**证据：** 第 923～931 行只阻止「已提交且 B 等于 A」的帧再次提交。曾修改过的帧因 B 始终不同于 A，可反复执行 `submitted++`、`modifiedFrames++` 和 `modifiedBoxes += modCount`。

**复现：** 修改第 190 帧 → 提交 → 返回 190 → 不做新编辑，再次提交。

**实测：** 计数从 190 增至 191，但真正 reviewed 的帧仍然只有 190 帧。已有完成任务还能出现 `1201 / 1200`。

**建议：** 分开判断「相对 A 是否修改」和「相对上次提交是否有新编辑」。进度以帧状态聚合为准，不无条件累加；重新提交替换当前有效版本，修改统计按该版本重新聚合。

### R03 · P1 · 视频状态、列表和帧状态不同步

**复现：** 打开待审查的 T20x_002.avi，提交第一帧。

**实测：** 右侧已有 1 帧提交，但视频状态仍为 pending；左侧仍显示「待审查」「0 / 850」。`submitFrame()` 不更新视频为 reviewing，也不刷新视频卡片。筛选数量是 HTML 写死的值。

**建议：** 首次正式提交将视频切为审查中，统一刷新列表、筛选数量和右侧统计。提供清晰的「当前帧未审查 / 已提交 / 重新编辑待提交」标签，避免用全局保存提示代替帧状态。

### R04 · P1 · 撤销没有恢复上一步，单纯点选也触发保存

**证据：** 第 819 行在拖动结束后把“修改后的”所有框坐标压入撤销栈，第 917 行又取出这一坐标恢复。

**实测：** 一个框从 `(127,33)` 移动到 `(145,42)`，第一次点击撤销后仍为 `(145,42)`，撤销栈反而清空。只点一下未移动的框也会增加撤销记录并显示保存中。

**建议：** 保存编辑开始前的快照；仅在几何真的变化时登记一次撤销并保存。点选对象不能作为修改。撤销后的状态与草稿同步刷新。

### R05 · P1 · 拖动时主框不跟手，放大后的坐标换算错误

**证据：** 第 785～787 行保存旧元素引用；第 791 行立即调用 `renderFrame()`，第 744 行替换整个画布内容。之后第 810～813 行仍在更新已经脱离页面的旧元素。

**实测：** 拖动中数据的 x 已从 127 变为 145，但可见框的 x 仍为 127，旧元素的 `isConnected=false`；松开鼠标重绘后框才跳到新位置。

第 796 行直接把屏幕位移当作原始像素位移，没有除以缩放比例。实测 150% 显示下横向拖 15 屏幕像素，数据移动 15px，正确应为 10px。

**建议：** 拖动期间保留并更新当前可见框，不重建其 DOM；使用画布逆变换换算坐标，移动和缩放统一处理。叠加 A 框、修改颜色及统计应同步刷新。

### R06 · P1 · 已提交/已完成结果仍能被直接改动，未生成固定 B 版本

**证据：** `startDrag()` 没有任务只读判断；`finishVideo()` 第 944～947 行仅更改 status 并显示「已固定审查版本 B」，没有生成快照。

**实测：** 打开标为已审查的 T20x_003.avi，仍能改变框；视频与帧仍保持 reviewed，修改处没有草稿提示。再次提交出现 `1201 / 1200`。

**建议：** 视频完成后读取不可变 B 快照，禁用编辑与提交。视频完成前再次编辑已提交帧，按文档实施建议转 pending、保留上一提交基线，支持重新提交或放弃恢复；不能静默修改已经提交的结果。

### R07 · P1 · 选择「继续检查」后，视频完成入口消失

**复现：** 全帧提交 → 完成弹窗点「继续检查」→ 希望稍后完成视频。

**实测：** 页面没有持续可用的「完成视频审查」入口；对未修改的已提交帧再次点击提交，只出现「本帧已提交，无新修改」，无法重新打开完成汇总。

**建议：** 全部帧已提交但视频未完成时，在右侧持续显示「全部帧已提交，待完成视频审查」和视频完成按钮。完成操作重新验证帧集合和状态。

### R08 · P1 · 1366×768 下画面被裁剪，存在漏审风险

**实测：** 该视口中画布容器可见高度为 412px，内部视频画布却为 480px，居中后上下各裁掉约 34px；容器使用 overflow:hidden。用户需要手工缩小才能看全。

**建议：** 初始采用适应窗口的显示比例；窗口缩放后保持画面完整可达，提供适应窗口/原始比例入口。放大时应可平移查看边缘；表格定位对象要保证该对象可见。列表筛选标签在此宽度也被挤成多行，应重新分配空间或采用可换行布局。

## 4. 已有入口但尚未完成的功能

### R09 · P1（断点续审）· 上次停留位置从未更新

`lastViewed` 只在初始模拟数据中赋值，导航时未写回。实测浏览到 192，任务仍保存 lastViewed=190；新视频访问后仍为 0。右侧「上次停留帧」直接显示当前帧，左侧则显示陈旧值，两者含义不一致。

继续审查找最早 pending 的算法已存在，但不能替代浏览位置的记录。应在帧成功加载后更新并保存 lastViewed；全帧已提交或已完成的任务不应仍用「继续审查将进入第1帧」提示。

### R10 · P2 · 快捷键已接入，但部分行为不符合 v1.1

| 问题 | 证据与影响 | 修正方向 |

| Esc 不取消拖动 | 第 1016～1018 行直接 return；实测 Esc 后松鼠标仍保留并保存修改 | 恢复手势开始前几何，移除拖动监听，不入撤销栈 |
| 系统快捷键被截获 | 单字母分支未排除 Ctrl/Meta/Alt；实测 Ctrl+F 把焦点切到帧号框 | 严格匹配修饰键；保留浏览器查找等默认行为 |

### R11 · P2 · 图像、播放、搜索和局部对比尚属占位

- 主画面创建了 canvas，但没有绘制视频帧，仅显示 CSS 背景和随机框，不能验证框是否真的包住目标。
- 局部对比有共同裁剪范围的计算，但只画框，没有裁剪帧图像，无法进行视觉质量对比。
- 播放按钮、时间轴没有事件实现；搜索框也不筛选列表。
- 时间显示统一按 33.3 秒计算，忽略每个视频自己的时间信息；拼接 `00:0${t}` 在较大时间会出现不规范格式。
- 修改类型函数未被使用，且所有修改分支都返回「已修改」，没有真正区分位置、尺寸及二者同时变化。

建议提供少量固定帧图片/视频和固定标注，先完成可复现的视觉演示。暂未实现的入口可明确标注或暂时隐藏，避免评审者以为可操作。

### R12 · 端到端功能缺口 · C 对比确认与可追溯数据未实现

顶部「对比确认」没有页面切换和业务行为；没有修改对象队列、C 采用 A/B、确认进度及最终版本。

现有数据是每帧的 a/b 几何副本和 status，缺少审查任务版本、提交历史、reviewer/time、稀疏 delta、固定 B 视频版本和 C 决定。框 ID 为每帧重复的 #001 等，单独使用无法唯一关联 A/B/C；至少应使用任务、帧、对象的稳定复合身份。

初始视频汇总声称有修改帧，但所有生成的 b 都等于 a；例如 v1 的 modifiedFrames=56 与逐帧数据实际修改帧数 0 不一致，无法用作可信的后续 C 输入。

如果该文件只承担 B 页面演示，C 完整页面可以后续制作；但本 demo 仍需至少产生固定 B 版本和差量列表，明确显示「待 C 对比确认」，而非仅弹一句已经固定版本。若以整个需求文档验收，此部分尚未完成。

## 5. 其他可用性与文案建议

- 「原始帧显示」应改为「原标注叠加」或「显示原框」，避免被理解为切换视频帧图像。
- 「完成全部帧的审查后，该视频将标记为已审查」应改为「所有帧提交后，点击完成视频审查」，与实际二级确认一致。
- 百分比目前取整，189/1000 显示 19%；按文档统一为 18.9%。
- 「第尚未浏览帧」应直接显示「尚未浏览」。
- 第一帧/最后一帧的边界导航按钮应禁用或给明确提示。
- 双向选中已有，但选中框或表格行在可视范围外时不自动定位；缩放后尤其明显。
- 当前帧分辨率、状态及视频修改框总数未完整呈现。
- 原型中所有帧随机产生 6～9 个对象，无法直接覆盖空帧；建议加入空帧和全部未修改的短任务。

## 6. 建议实施顺序

1. **先修编辑和数据错误：** 主框拖动跟随、缩放坐标、撤销、纯点选不保存、重复提交计数、完成后只读。
2. **补全审查状态闭环：** 首次提交进入审查中、列表联动、逐帧状态、重新编辑、持续可用的视频完成入口。
3. **实现可恢复的演示数据：** 固定 A、逐帧草稿、保存/放弃/恢复、lastViewed 和完成 B 快照。原型可以先用本地存储。
4. **完善可见性与键盘：** 自动适应画面、定位联动、Esc、修饰键隔离、输入校验、macOS 提示与弹窗焦点。
5. **补演示素材和 C 衔接：** 真实帧与局部裁剪、播放/搜索、差量队列和最终 A/B 选择。

建议先制作一个 3～5 帧、包含无框帧和修改帧的小任务，能完整演示“浏览不提交 → 修改保存 → 刷新恢复 → 明确提交 → 继续检查 → 完成视频 → C 选择”。这样的短任务比堆出数千帧随机数据更容易验证需求。
