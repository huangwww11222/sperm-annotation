## 1. 结论

**已有多项重要修复，但仍有阻断项，不建议将这一版标记为“需求验收通过”或直接照搬为正式开发的状态与保存逻辑。**

当前可以作为页面布局与基础操作的参考。正式开发前，仍需明确并修复：已提交帧再次编辑、保存失败反馈、草稿恢复/放弃、浏览位置恢复、固定 B 版本的保存，以及只读状态下的正常查看。

本轮没有修改 HTML。检查方式为源码审查和独立 Chrome 浏览器会话中的鼠标、键盘、刷新与视口实测；保留了第一轮报告，本文记录第二轮结果。视频完成测试通过临时设置浏览器内的帧状态覆盖末帧场景，没有改动源文件；保存失败测试通过临时模拟存储写入异常完成，不代表正常情况下每次保存都会失败。

原型可以继续使用本地存储和模拟数据，不要求此时实现生产后端。判断是否可用于开发的重点，是交互与状态是否完整、准确，而不是是否已接入真实接口。

## 3. 开发前需要解决的阻断项

### B01 · P1 · 再次编辑已提交帧，没有重新进入待提交状态

**位置：** 第 844～909 行 `startDrag/endDrag`；第 1024 行只在 `undo` 中处理 reviewed → pending；第 934～942、1066～1076 行视频完成逻辑。

**复现与实测：**

1. 打开一帧已提交的帧，直接移动框。
2. 新坐标产生并保存，但帧仍为 reviewed，已审查帧数不减少，局部对比也不出现草稿标识。
3. 在全帧已提交场景，选择“继续检查”后再次移动一个框，不重新点击提交本帧。
4. “完成视频审查”仍可执行，把这次未明确提交的编辑包含进 B 快照。

实测完成汇总仍显示修改帧数 0，而新编辑已经进入当前数据；说明统计与将要固定的结果可以不一致。

**影响：** “草稿 ≠ 提交本帧”的核心规则被绕过。其他帧的提交还会聚合这些仍标为 reviewed 的可变数据，使未提交编辑混入视频统计。

**修复要求：**

- 发生实际几何变化时，将该帧置为 pending，保存上一有效提交基线，更新进度并提示需重新提交。
- 单纯选中、取消拖动、无几何变化不使提交失效。
- 保存草稿与正式提交结果使用不同字段/记录；重新提交后才更新有效提交版本。
- 完成视频时检查实际帧状态和未提交编辑，不能仅判断缓存的 `submitted >= frames`。
- 完成汇总与快照从同一组有效提交结果产生。

这是本轮最需要先修复的问题。

### B02 · P1 · 固定 B 快照未持久化，刷新后消失

**位置：** 第 685～714 行保存/加载结构；第 1069 行创建 `bSnapshot`。

**实测：** 完成视频后，内存中 `bSnapshot` 存在，但 localStorage 的对应视频对象中没有这个字段；刷新后视频仍为 reviewed，`bSnapshot` 却不存在。

**边界说明：** 当前框数据仍保存在 framesData 中，本问题不等于所有 B 坐标都丢失。丢失的是宣称已经固定、应作为 C 输入的独立版本快照及其身份。

**修复要求：** 保存并恢复独立 B 完成版本，包含版本 ID、A 基准引用、完成时间、完成者及各帧提交引用/快照。只读页面和未来 C 页面读取这个版本，而不是可变工作区。即使尚未制作 C 界面，该输出契约也应确定。

### B03 · P1 · 保存失败仍显示成功，提交也不会被阻止

**位置：** 第 696～697 行吞掉写入异常；第 902 行定时显示“草稿已保存”；第 1047～1057 行先标提交并继续跳转。

**受控故障实测：** 让本地写入抛出存储异常后移动框，页面仍显示“草稿已保存”；刷新后刚才编辑丢失。

**修复要求：** `saveState` 返回明确成功/失败，失败时显示未同步、保留编辑并允许重试。只有写入成功后才显示已保存；提交失败应停留当前帧，不显示成功、不推进流程。视频完成同样必须遵守成功确认。

普通路径已使用真实 localStorage，比上一版有进步，但错误路径目前会误导用户。

### B04 · P1 · 缺少完整的草稿恢复与放弃流程

**实测：** 修改帧后刷新，几何可恢复，但只显示通用“继续上次审查”弹窗；没有“本帧有未提交修改”的专门提示，没有“继续编辑 / 放弃修改”。保存栏恢复为“无待保存内容”，没有清楚说明存在已保存但未提交的草稿。

**结构原因：** 仍把编辑中的 B 坐标直接放在帧对象里，没有区分当前草稿和上一正式提交。特别是重新编辑已提交帧时，无从实现“放弃并恢复上次 B 提交”。

**修复要求：** 为草稿提供独立身份、更新时间和编辑基线，恢复时显示未提交状态。首次审查放弃草稿恢复 A；重新编辑放弃草稿恢复上一有效 B 提交。不要简单将所有放弃操作重置为 A。

## 4. 仍需修复的流程与操作问题

### F01 · P2 · lastViewed 在内存中更新，但没有正确保存和展示

**位置：** 第 759～775、794、1009～1015 行。

存在两个独立问题：

1. 浏览第 190 → 191 → 192 帧后，内存 lastViewed=192，但持久化值仍为 190，因为导航不调用保存；刷新后停留记录丢失。
2. `selectVideo` 先调用 `renderFrame` 改写 lastViewed，再构造恢复弹窗。S20x_005 原来停在 321，首个 pending 是 231，实测弹窗却说“上次停留第231帧”。这把本次默认目标冒充成历史位置。

另一个结果是：新视频首次打开也先被写为 lastViewed=1，然后弹出“继续上次审查”，失去区分首次访问的能力。

**修正：** 先保存历史位置变量并构造恢复信息；当前帧成功展示后再更新浏览位置、刷新卡片并持久化。渲染选中高亮等动作不应承担保存历史语义。继续审查仍去首个 pending，但历史位置要真实显示。

### F02 · P2 · 只读模式把正常浏览也禁用了

**位置：** 第 846、1010、1014、1112、1122 行。

已完成视频的拖动保护有效，但上一帧、下一帧、方括号选框以及直接点击画面选框也被提前 return 阻止。实测已审查视频点击下一帧没有反应，而输入帧号仍可跳转，操作不一致。

提交按钮仍显示为可点击，只是在点击后提示不允许。

**修正：** 禁止几何编辑、撤销和提交；保留导航、画面与表格选中、对照查看、原框叠加和帮助。禁用不可执行的提交按钮并显示已审查状态。

### F03 · P2 · 键盘和按钮的帧号校验不一致

**位置：** 第 1194～1213 行键盘处理；第 1273～1276 行按钮处理。

输入 `2.7` 后按 Enter 会提示“请输入有效的整数帧号”；同样输入后点击“确定”，仍被 `parseInt` 转为第2帧并跳转。

**修正：** 把输入校验与跳转封装为一个动作，Enter 和按钮调用同一实现。其他保存、提交入口也应采用同样原则，避免分别修复造成分叉。

### F04 · P2 · 当前帧状态、保存提示与操作仍有歧义

- 提交第190帧后自动进入尚未提交的191帧，右侧仍显示“本帧已提交”，会让用户误以为191已经完成。
- 没有独立、持续显示的当前帧 pending/reviewed 标记；不能依赖全局保存提示表达正式状态。
- 已提交且没有新编辑的帧仍可再次点击提交，虽然计数已不重复，但按钮状态与文档不一致。
- 旧帧的保存定时器未绑定帧身份，切帧后仍可能更新新帧提示。

**修正：** 分开显示帧业务状态、未提交编辑状态和保存结果，异步回执关联任务/帧/版本。自动跳转后若保留成功提示，应写“第190帧已提交”，并明确新帧未提交。

## 6. 最小复验标准

解决下列场景后，才建议将 B 的交互流程视为基本定稿：

1. 首次编辑 → 保存成功 → 刷新 → 显示草稿恢复选择，继续或放弃均得到正确结果。
2. 已提交帧再编辑 → 变待提交、进度减少 → 此时不能完成视频 → 重新提交后才可完成。
3. 已提交帧再编辑后放弃 → 恢复上一有效提交及进度，保留A基准不变。
4. 模拟保存失败 → 显示未同步并停留，不出现成功提示、不假提交或假完成。
5. 仅浏览到另一帧再刷新 → 正确显示真实历史停留点，默认续审仍定位最早未审查帧。
6. 全帧提交后继续检查 → 视频完成入口持续可用，但有新未提交编辑时禁用。
7. 完成视频并刷新 → 固定B版本和来源信息仍可读取；只能查看，但正常导航、选框不受阻。
8. 键盘Enter和鼠标确定对同一输入给出相同结果，当前帧状态不被上一帧成功提示混淆。

建议用3～5帧固定演示任务走完上述闭环，再以该任务作为正式开发的验收样例。真实数据接入、后端并发控制、权限和C最终确认仍需按需求文档单独验证，本轮浏览器测试不能替代这些验收。
