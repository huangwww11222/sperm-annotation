# 审查模式原型：最终审查与开发交接

## 1. 最终意见

**该原型已可作为页面布局和常规 B 审查流程的开发参考，但尚不能判定为全部需求验收通过。**

可以以“需求文档 + 当前原型 + 本报告的必修项”启动正式项目开发。开发时必须纠正下文的失败回滚、草稿处理及只读查看问题，不应将当前 HTML 作为唯一规格或直接照搬其保存逻辑。

本轮进行了30组浏览器测试记录，覆盖常规操作、刷新恢复、末帧完成、受控存储失败、坐标计算与视口适配。30组表示测试范围，不表示全部通过。HTML未改动。

测试使用独立Chrome会话；末帧场景在浏览器内设置完整帧状态，空帧场景使用受控数据，保存失败通过临时模拟存储写入异常验证。未接真实业务后端、真实视频或C页面，因此这些部分不在本轮通过范围。也没有核验未提供的原型图片像素一致性。

## 3. 必须纳入正式开发的修正项

### P1-01：提交失败污染上一有效提交基线

**位置：** `submitFrame()`第1120～1135行，尤其第1124行；`discardDraft()`第768～774行。

当前提交顺序是：先覆盖`committedB`，再保存。如果保存失败，只恢复部分状态，没有恢复旧的`committedB`及全部相关任务字段。

**实测一：首次提交失败。** 第190帧有草稿，提交时模拟写入失败。界面显示失败，帧仍pending；恢复存储能力后重新打开视频并选择“放弃修改”，该帧却变成reviewed，进度从189增至190，修改依然保留。一次失败提交被后续放弃动作当成了有效提交。

**实测二：重新提交失败。** 先成功提交B1，再编辑成B2，模拟B2提交失败。选择“放弃修改”后恢复的是失败的B2，成功提交的B1基线已经被覆盖。

**正式开发要求：**

- 候选提交不能在写入成功前成为有效`committedB`。
- 将帧状态、提交基线、草稿标记、视频状态、统计更新作为一个完整事务处理。
- 失败保留原有效提交与当前待处理草稿；不要通过局部回滚留下混合状态。
- 生产服务端采用事务、版本校验和幂等请求，前端以服务端成功结果更新有效状态。

这是本轮最高优先级问题。

### P1-02：放弃与导航没有统一的保存失败处理

**位置：** `discardDraft()`第783～785行；第1080～1084行帧导航；第1253行跳转；第801行视频切换保存。

**实测：** 放弃草稿时模拟写入失败，页面仍显示“已放弃修改”；刷新后被放弃的草稿重新出现。普通草稿保存失败后仍可直接进入下一帧；没有明确重试入口或统一的离页处理。

**正式开发要求：**

- 保存、提交、放弃、切帧、换视频使用一致的保存结果协议。
- 放弃失败不能显示成功，须保留/恢复原状态并允许重试。
- 有未同步编辑时，按需求先成功保存再导航；失败则停留，提供重试或明确放弃操作。
- 异步反馈绑定任务、帧和版本，避免旧帧定时器修改新帧提示。

**同类残留：** 视频完成保存失败会回滚video.status，但失败创建的`bSnapshot`仍留在内存。后续其他保存可能把这个未成功完成的快照一并保存；失败路径必须恢复快照引用，而不只是改一个状态字段。

### P2-01：历史已审查帧缺少有效提交基线

**位置：** 第671～681行初始帧数据、第765～778行放弃判断。

初始标为reviewed的帧没有`committedB`。实测进入原先已提交的第189帧，编辑后再放弃，帧没有恢复reviewed，而是变成pending；进度从189降至188。

**正式开发要求：** 每个reviewed帧都必须指向真实有效提交记录。加载已有任务时建立/验证基线，不用“有没有committedB字段”代替“此前是否有效提交”的业务判断。当前seed数据也应保持该不变量，避免开发者把错误初始化逻辑带入真实数据导入。

### P2-02：草稿恢复只覆盖打开视频时的首个pending帧

**位置：** 第789～817行，恢复提示仅在`selectVideo()`中执行。

**实测：** 第190帧未提交，第191帧保存了草稿。刷新后默认进入190，提示中没有191草稿入口；导航至191后虽加载了草稿几何，也没有“继续编辑/放弃修改”入口。现有放弃按钮仅在视频打开时的弹窗里。

**正式开发要求：** 每帧具有稳定的草稿状态和可访问的放弃入口；加载任意有草稿的帧都能按规则处理。默认续审仍指向最早pending，同时提示其他位置的草稿。可以使用持续的草稿提示条，避免每次切帧都强制弹窗，但不能让用户无法放弃。

### P2-03：只读视频仍不能直接点击画面选框

**位置：** 第905～907行`startDrag()`在设置selectedId前直接返回。

本轮只读视频的左右导航、键盘选框已通过，提交按钮已禁用。但鼠标点击画面中的框仍不选中，局部对比不随之切换；表格选框则可用。

**正式开发要求：** 对象选择与几何编辑分离。只读时允许点击查看和三处联动，禁止开始拖动/缩放。只读框不应显示可编辑控制柄或“拖动调整”提示。

### P2-04：无净变化的拖动也使提交失效

**位置：** 第930～931行`dragMoved=true`，第959～965行据此转pending。

**实测：** 在已提交帧中把框移开再移回原位后松手，最终全部几何与手势前完全相同，但帧仍变pending、出现草稿、已审查帧数减少。

**正式开发要求：** 用规范化后的最终几何与编辑基线比较，决定是否真正产生待提交变化，不能仅依据发生过mousemove。相对A是否修改和相对上一提交是否有新编辑要分别判断。

## 4. 正式开发的范围和实现约束

以下仍未在原型中完整实现或验证，应进入明确的开发与验收计划，而非视为通过项目验收。

### 4.1 真实媒体与可见性

主画面仍是背景和框，局部对比仍未裁剪真实视频帧。播放、时间轴和搜索入口没有完整行为；时间仍按统一33.3秒计算。需要用真实帧验证坐标变换、A/B共同裁剪范围、时间戳、框边界及放大后的可达性。

默认适应窗口已通过；用户手动放大后的平移、重新适应窗口入口、选中对象自动定位，仍需实现。保留的入口应可用，暂不实现的入口应明确标记。

### 4.2 数据身份与正式版本

原型内`#001`等ID在各帧重复，真实系统需采用稳定的任务/帧/对象身份或明确复合键。A必须绑定不可变基准版本；帧提交、草稿和视频B完成版本分别管理。

当前新B快照已经可持久化，但只读页面仍主要读framesData；正式项目应明确读取固定完成版本。预置的“已审查”视频没有对应B版本快照，也应补齐初始化数据。

初始修改帧/框汇总与随机A=B数据仍不一致，正式统计必须从当前有效提交版本推导。不要沿用演示用的写死计数。

### 4.3 C对比确认

当前未实现C的修改对象队列、采用A/B、确认进度及最终标注。正式开发应明确：

1. C仅接收已成功固定的B版本中的修改对象。
2. 未修改对象自动沿用A。
3. C逐对象选择A/B，不覆盖A或B历史。
4. 所有待确认对象已决定后，固定最终版本并记录来源。
5. 零修改任务的收尾按需求文档约定处理。

若本次只开发B页面，C可以独立排期，但B输出的数据契约必须先确定。

### 4.4 保存、权限与并发

原型全量localStorage保存不代表服务端可靠性已验收。正式开发要实现按帧保存、身份鉴权、字段权限、幂等、版本冲突和事务；客户端隐藏按钮不能替代服务端禁止增删框和改类别。

undoStack不等于提交历史。避免把所有视频和无限撤销记录每次全量序列化；规定历史保留范围及草稿更新机制。

### 4.5 交互细节

- 已提交无新编辑的帧应显示已提交并禁用重复提交入口。
- 首次草稿宜显示“未提交修改”，不要统一写“待重新提交”。
- macOS帮助与按钮提示适配⌘；帮助入口和弹窗支持键盘焦点。
- 输入法隔离已有代码，本轮未进行真实中文输入法端到端测试。
- 统一坐标存储与显示精度，避免拖动后表格出现长小数。
- 修改类型推导目前仍未完成，不能把所有情况都当成同一种“已修改”。

## 5. 项目交接时应采用的验收门槛

| 场景 | 必须得到的结果 |
| --- | --- |
| 首次提交失败后放弃 | 恢复A且仍pending，不凭失败记录增加已提交帧数 |
| B1成功、B2提交失败后放弃 | 精确恢复B1，保留B1作为有效提交 |
| 放弃草稿的写入失败 | 显示失败并可重试，不声称已经放弃 |
| 有未同步修改时导航 | 按统一离页规则处理，不能悄悄遗留未保存编辑 |
| 导入已有reviewed帧后编辑并放弃 | 恢复导入的有效提交、状态与进度 |
| 非最早pending帧存在草稿 | 可发现、恢复或放弃该帧草稿 |
| 已提交帧拖回手势前位置 | 几何无净变化时不使有效提交失效 |
| 完成视频保存失败 | 不留下被当成正式完成结果的快照 |
| 完成后刷新 | 固定版本可读，能正常导航、点选和对比，不能编辑 |
| 真实视频与C流程 | A/B几何、差量队列、采纳决定和最终来源全部可追溯 |

最终交接结论：**布局与常规审查路径可用；失败事务和少数状态边界仍需修正。可以启动项目开发，但必须将本报告列为实现与验收依据，不能把当前HTML解释为已经通过完整需求验收。**
