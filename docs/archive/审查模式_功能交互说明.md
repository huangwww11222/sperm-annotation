# 微流控精子识别与提取平台：「审查模式」功能交互说明

版本：1.0

面向对象：产品、交互设计、前后端开发、测试及实现 Agent  
需求来源：[分支 · 标注审查流程设计](chatgpt-conversation://6ab7acf8-a338-83eb-97e8-6589d18e0c7c)

## 1. 文档范围与约定

本文依据原对话中已确定的业务逻辑及文字版页面说明整理，覆盖审查员 B 的页面、状态、保存与恢复，以及第三人 C 的对比确认衔接。原对话可读取内容中没有可供核验的原型图片附件，因此本文定义区域和交互，不将像素尺寸、间距等视觉细节视为已确认要求。

文中「已确认规则」是原对话明确提出并用于后续设计的业务约束。「实现补充」用于填补原对话未定义的边界，给出可落地的默认方案，不表示这些细节已经经过用户逐项确认。数据表、字段名和接口名均为建议契约，可映射到现有系统，但业务含义必须保持一致。

三个必须始终成立的区别：

1. 浏览某帧，不等于该帧已完成审查。
2. 自动保存草稿，不等于提交本帧。
3. 所有帧已提交，不等于视频自动变为「已审查」。

## 2. 页面定位、角色与权限

审查模式面向已经完成原始标注的视频，用于发现并修正已有框的位置、尺寸问题。B 无需重新标注，也无需逐框点击「正确」；正确框保持不动，只有需要修正的框才进行操作。但每一帧都必须由 B 显式提交。

| 角色 | 职责 | 产出 | 权限边界 |
| --- | --- | --- | --- |
| 标注员 A | 完成视频原始标注 | 原始标注版本 A | A 完成后的基准版本在本流程中永久保留 |
| 审查员 B | 逐帧检查并移动、缩放已有框 | 帧提交记录、B 修改差量、完整审查版本 B | 不覆盖 A；不能新增、删除、复制框，不能新建或修改类别 |
| 第三人 C | 对 B 修改的对象逐项比较 A 与 B | 对象级采纳决定、最终标注版本 | 在 A、B 中决定采用哪个；重新画框、第三种几何版本不在当前范围 |

### 2.1 已确认业务约束

| 事项 | 规则 |
| --- | --- |
| 可审查视频 | 仅限原始标注已经完成的视频 |
| B 可修改内容 | 已有框的位置 x/y、宽高 w/h |
| 修改方式 | 拖动框内部移动；拖动边角缩放；无需切换工具 |
| 原始标注 | 不可被 B 或 C 覆盖，保留来源与对象身份 |
| 修改类型 | 由系统根据几何差异推导，不要求手工选择 |
| 修改原因及问题标记 | 不要求填写原因，不提供「标记问题」流程 |
| 正确框 | 不操作，B 的有效结果自动沿用 A |
| 指标 | IoU、中心位移、宽高变化，用于描述 A 到 B 的差异 |
| 不纳入的指标 | Precision、Recall、F1、TP、FP、FN |
| 撤销 | 撤销当前帧最近一次修改；当前范围不要求重做 |
| 帧完成 | 必须点击「提交本帧」，无修改的帧也必须提交 |
| 视频完成 | 所有帧提交后，B 再点击「完成视频审查」 |
| 中途退出 | 保存浏览位置、已提交进度及已成功保存的未提交草稿 |
| 最终版本 | B 的结果是建议版本，最终采用结果由 C 确认流程生成 |

## 3. 端到端流程与数据版本

```text
视频 → A 完成标注 → 自动入库并固定原始标注版本 A
                              │
                              ├───────────── 永久保留 A ─────────────┐
                              ↓                                      │
                         B 逐帧审查                                  │
                    ┌─────────┴─────────┐                            │
                  框正确              框需修正                       │
                  不修改              移动 / 缩放                    │
                    │                 自动保存草稿                   │
                    └─────────┬─────────┘                            │
                              ↓                                      │
                         显式提交本帧                                │
                              ↓                                      │
                  所有帧已提交 + 完成视频审查                         │
                              ↓                                      │
                    固定审查版本 B = A + B 差量                      │
                              └──────────────┬───────────────────────┘
                                             ↓
                                   C 只处理 B 修改的对象
                                      选择采用 A 或 B
                                             ↓
                                     生成最终标注版本
```

「A + B 差量」表示按稳定对象 ID 替换几何字段，不是增加对象。B 未修改的对象直接复用 A。草稿、帧提交结果、视频完成版本和最终版本是不同层次的数据，不得共用一个会互相覆盖的结果字段。

## 4. 页面总体结构

```text
┌─────────────────────────────────────────────────────────────────┐
│ ① 顶部流程导航：标注 → 自动入库 → 审查模式 → 对比确认             │
├───────────────┬───────────────────────────────┬─────────────────┤
│ ② 视频列表    │ ③ 视频审查主区域              │ ④ 统计与操作    │
│ 筛选、状态    │ 当前帧、已有框、选中与编辑    │ 当前帧修改统计  │
│ 进度、停留点  │ 原框叠加、帧导航与跳转        │ 撤销、提交本帧  │
│               │                               │ 视频进度        │
├───────────────┴─────────────┬─────────────────┴─────────────────┤
│ ⑤ 原始标注 / 审查后局部对比 │ ⑥ 当前帧标注框对比表              │
└─────────────────────────────┴───────────────────────────────────┘
```

### 4.1 区域①：顶部流程导航

- 展示「标注 → 自动入库 → 审查模式 → 对比确认」，当前「审查模式」高亮。
- 导航用于说明数据生产阶段；切换页面本身不提交帧、不完成视频、不改变最终版本。
- B 的草稿及未完成视频不进入 C 的正式处理队列。
- **实现补充：** 导航切换遵循第 10 节的保存与离页规则；没有相应权限时不开放目标操作。

### 4.2 区域②：待审查视频列表

数据来源：已完成 A 标注且进入审查任务的视频。筛选项为「全部、待审查、审查中、已审查」，各自展示数量；数量使用同一权限和任务范围计算。

每个视频卡片展示：

| 字段 | 含义及示例 |
| --- | --- |
| 文件名 | `T20x_001.avi` |
| 视频时长 | 视频媒体元数据给出的时长 |
| 总帧数 | `1000 帧`，与当前审查任务的帧集合一致 |
| 视频状态 | 待审查 / 审查中 / 已审查 |
| 已提交进度 | `189 / 1000 帧 · 18.9%` |
| 上次停留 | `第 190 帧`；第一次进入可显示「尚未浏览」 |
| 草稿提示 | 有未提交草稿时显示简短提示，不折算为进度 |

点击视频：先处理当前编辑的保存，再加载目标任务与恢复提示。点击「查看第1帧」只切换浏览位置，不清空已提交结果、草稿或进度。

### 4.3 区域③：视频审查主区域

顶部信息包含文件名、`第 N / 总帧数 帧`、当前帧时间 / 总时长、视频原始分辨率、当前帧审查状态及草稿保存状态。时间来自帧时间戳；不要仅靠帧号推算可变帧率视频的时间。

主画面展示当前帧和全部已有框。框在屏幕上的大小随画布缩放变化，但持久化坐标始终使用原始视频像素坐标。

框的视觉状态：

| 状态 | 视觉及行为 |
| --- | --- |
| 未修改 | 建议绿色实线；当前几何与 A 一致 |
| 已修改 | 建议红色或高亮实线；当前几何与 A 不同 |
| 选中 | 边框高亮并显示角点控制柄；不改变修改状态 |
| A 原框叠加 | 建议紫色虚线，只读，不接收编辑操作 |

颜色须配合线型、文字或图例表达状态。选中状态与是否修改独立，不能因为选中而被统计为修改。

「原标注显示」提供「隐藏原框、叠加显示」。隐藏仅指隐藏额外绘制的 A 对照层，当前有效框仍显示。叠加模式下，修改对象显示 A 和 B 两套框；未修改对象不必重复绘制。

下方提供上一帧、下一帧、输入帧号跳转。若存在播放或时间轴拖动，它们也仅改变浏览位置，不改变帧审查状态。进入第一帧时禁用上一帧；进入最后一帧时禁用下一帧；跳转值必须为范围内整数。**实现补充：** 编辑框时暂停播放，防止在切帧过程中写入错误帧。

### 4.4 区域④：当前帧统计与审查操作

当前帧统计跟随当前有效几何实时更新：

| 项目 | 统计口径 |
| --- | --- |
| 当前帧标注框数 | A 在当前帧的对象总数 N |
| 已修改框 | 当前有效几何与 A 不同的对象数 M |
| 未修改框 | N − M |
| 平均 IoU（修改框） | 仅对 M 个修改框计算算术平均；M = 0 时显示 `—` |
| 最大位置偏移 | 修改框中最大的中心位移；M = 0 时显示 `—` |

帧操作区提供「撤销」和「提交本帧」。视频信息区展示已提交帧数、总帧数、百分比、已提交结果中的修改帧数与修改框数。草稿变化会影响当前帧实时统计，但不会混入视频级已提交统计。

当所有帧提交完毕，显示视频完成汇总及「继续检查 / 完成视频审查」。用户关闭汇总或选择继续检查后，仍能重新找到「完成视频审查」入口。

### 4.5 区域⑤：原始标注 / 审查后局部对比

选择对象后并列显示「原始标注 A」与「审查后（当前）」：同一帧图像、同一对象 ID、两侧局部图像、各自 x/y/w/h。

**实现补充：** 两侧使用相同裁剪范围和缩放比例。裁剪范围包含 A 框与当前框的并集及适量上下文，防止独立裁剪后将位移视觉上抵消。当前为草稿时明确标为「审查后（草稿）」，避免误认为已经提交。

未选中对象时显示「请选择一个标注框查看对比」；没有对象时显示空状态。该区域默认只读，编辑统一在主画面进行。

### 4.6 区域⑥：当前帧标注框对比表

表格展示当前帧全部对象，而不只展示修改对象。

| 列 | 内容 |
| --- | --- |
| ID | 稳定对象 ID；界面可显示简短编号，但数据关联使用完整 ID |
| 原始标注 A | x / y / w / h |
| 审查后（当前） | 当前有效 x / y / w / h；有草稿时明确提示 |
| 状态 | 未修改 / 已修改，可附系统推导的修改类型 |
| IoU | 修改框显示数值，未修改显示 `—` |
| 位置变化 | 中心位移，单位 px |
| 尺寸变化 | 带正负号的 Δw / Δh，单位 px |
| 操作 | 查看 |

点击行或「查看」后：主画面选中并高亮对象，必要时将对象移入可视范围，局部对比同步切换。反向点击画面中的框时，表格选中对应行并使其可见。整个页面维护同一个 `selected_annotation_id`。

## 5. 框编辑、撤销与差量判定

### 5.1 加载与选中

进入一帧时先读取 A、帧已提交结果及草稿元信息。有草稿时按恢复选择加载；没有草稿时加载当前已提交 B 结果；没有已提交结果时使用 A。

点击当前框选中；点击空白取消选择。A 对照框只读。选中、悬停、滚动、缩放、查看对比均不产生修改差量。

### 5.2 移动与缩放

拖动框内部改变 x/y；拖动角点改变框边界。缩放左侧或上侧边界时可能同时改变 x/y 和 w/h。系统实时刷新框、对比图、表格及统计；拖动结束后形成一次可撤销操作，并自动保存草稿。

**实现补充：** 坐标原点在原始帧左上角，x 向右、y 向下；框必须满足 `x ≥ 0、y ≥ 0、w > 0、h > 0、x+w ≤ 图像宽、y+h ≤ 图像高`。移动到边界时限制在图像内；缩放禁止翻转成负宽高。前后端使用同一规范，后端拒绝非法几何。

### 5.3 修改状态和类型

所有修改判断均相对于 A，而不是相对于上一次鼠标操作：

```text
position_changed = (xB != xA) or (yB != yA)
size_changed     = (wB != wA) or (hB != hA)

二者都为 false → 未修改
仅 position_changed → 位置调整
仅 size_changed     → 尺寸调整
二者都为 true      → 位置 + 尺寸调整
```

该类型沿用原对话的坐标字段判定，不用于描述用户使用了哪一种手势。中心位移是另一项独立数值：即使 x/y 不变，只改变宽高也可能使中心移动。

若最终几何恢复到 A，当前 B 结果中移除该对象差量，修改框计数减少，IoU 表格显示恢复为 `—`。保留操作审计记录不等于保留有效差量。

**实现补充：** 优先沿用原始标注的坐标精度规范，不因显示取整修改 A；持久化比较前对编辑结果作统一规范化。前后端不能分别使用不同的浮点容差。若原数据没有精度规范，实施时需选择并记录固定精度；不要用显示为 `1.00` 的 IoU 判断是否修改。

### 5.4 撤销

「撤销」或 `Ctrl+Z` 恢复当前帧最近一次完整编辑前的几何，再重新计算差量并自动保存。**实现补充：** macOS 同时支持 `⌘Z`；焦点在文本输入框时保留原生文字撤销行为。

一次拖动对应一次撤销，不按鼠标移动采样点逐次撤销。没有可撤销操作时按钮禁用。当前范围不要求跨帧、跨会话恢复撤销历史，也不要求重做。撤销只影响编辑结果，不能代替撤回已提交业务记录。

## 6. IoU、位移和尺寸变化

### 6.1 坐标约定

框表示为 `(x, y, w, h)`，对应连续像素坐标区间 `[x, x+w) × [y, y+h)`，面积为 `w×h`。不要在交集宽高计算中额外加 1。

### 6.2 IoU

```text
intersection_w = max(0, min(xA+wA, xB+wB) - max(xA, xB))
intersection_h = max(0, min(yA+hA, yB+hB) - max(yA, yB))
intersection   = intersection_w × intersection_h
union          = wA×hA + wB×hB - intersection
IoU            = intersection / union
```

合法框下 IoU 在 `[0,1]`，没有交集时为 0。A 和 B 完全一致时数学值为 1，但未修改框在页面中显示 `—`，不进入平均值。非法零面积框属于数据错误，不能用 `0` 或 `1` 掩盖。

这里的 IoU 仅表达 A 与 B 的重叠程度，不是识别模型的准确率，也不能证明 B 比 A 更正确。不设置未经确认的阈值来自动判错、拦截提交或代替 C 选择。

### 6.3 位置变化

```text
CA = (xA + wA/2, yA + hA/2)
CB = (xB + wB/2, yB + hB/2)
delta_cx = CB.x - CA.x
delta_cy = CB.y - CA.y
center_shift_px = sqrt(delta_cx² + delta_cy²)
```

位置变化展示中心点欧氏距离，单位是原始视频像素 px，不是屏幕缩放后的像素。可保存带符号的分量用于复核。尺寸改变也可能造成中心位移。

### 6.4 尺寸变化

```text
delta_w = wB - wA
delta_h = hB - hA
```

展示例如 `Δw +2 px / Δh +2 px`，或有明确表头时显示 `+2 × +2 px`。零变化显示 0，缩小显示负数。当前需求不要求尺寸变化百分比。

### 6.5 核算后的统一示例

| 项目 | A | B |
| --- | --- | --- |
| x / y | 512 / 336 | 520 / 338 |
| w / h | 24 / 24 | 26 / 26 |
| 中心 | (524, 348) | (533, 351) |
| 面积 | 576 | 676 |

交集为 `16 × 22 = 352`，并集为 `576 + 676 − 352 = 900`，所以：

- `IoU = 352/900 ≈ 0.391111`，界面显示 `0.39`。
- 中心变化为 `(+9, +3) px`，中心位移 `√90 ≈ 9.486833 px`，界面显示 `9.5 px`。
- 尺寸变化为 `Δw +2 px / Δh +2 px`。
- 修改类型为「位置 + 尺寸调整」。

原对话示意中的 `0.68 / 6.4 px` 与上述坐标不匹配，本版统一采用核算值。建议 IoU 展示两位小数、位移一位小数；存储和聚合使用未作展示舍入的数值。

## 7. 帧级状态与提交

### 7.1 正式状态与草稿状态独立

| 状态字段 | 值 | 含义 |
| --- | --- | --- |
| `frame.review_status` | `pending` | 尚未提交有效的本帧审查结果 |
| `frame.review_status` | `reviewed` | B 已显式提交本帧 |
| `draft_exists` | true / false | 是否有未提交编辑，不代表审查完成 |
| 界面保存状态 | 无待保存内容 / 保存中 / 已保存 / 保存失败 | 描述草稿持久化是否成功，不是业务状态 |

首次审查的典型状态：

```text
pending，无草稿
  ├─ 浏览或切帧 ───────────────→ pending，无草稿
  ├─ 修改并自动保存 ───────────→ pending，有草稿
  └─ 无修改但提交本帧 ─────────→ reviewed，无草稿

pending，有草稿
  ├─ 继续编辑并自动保存 ───────→ pending，有草稿
  ├─ 放弃草稿 ────────────────→ pending，无草稿
  └─ 提交本帧成功 ────────────→ reviewed，无草稿
```

### 7.2 「提交本帧」的行为

1. 暂停本帧编辑，取点击时的完整有效几何和版本号，显示「提交中」。
2. 等待或合并同帧待保存请求，保证提交携带最新编辑，不提交旧草稿快照。
3. 服务端验证任务可编辑、A 版本一致、对象集合与类别未改变、框合法、编辑版本未冲突。
4. 服务端相对于 A 重新计算差量、修改类型、IoU、位移与尺寸变化。
5. 在同一事务内保存帧提交版本、设置 `review_status=reviewed`、记录提交人和时间、清除对应已提交草稿、更新进度与汇总。
6. 返回服务端确认的帧结果和视频统计；页面显示「本帧已提交」。
7. 进入下一个未审查帧；若全部提交，打开视频完成汇总。

**实现补充：** 自动跳转先找当前帧之后的最小未审查帧；没有则回到全视频最小未审查帧，防止遗漏更早的空缺。失败时停留当前帧、保留编辑并提示重试，不提前加进度、不跳转。

重复点击或网络重试必须幂等，同一帧不会重复增加已审查帧数。已经提交且没有新编辑的帧显示「已提交」并禁用提交按钮。

### 7.3 无修改及空帧

没有修改时也写入帧提交记录，`modified_box_count=0`，不创建无意义的对象差量。**实现补充：** A 在某帧没有任何框时，该帧仍属于任务的完整帧集合，需显式提交，框数为 0；不能靠「无框」自动跳过或视为已审查。

### 7.4 已提交帧再次编辑：实现补充

原对话允许返回已看过的帧，但未完整定义再次编辑的状态。为使修改与提交语义一致，建议采用以下规则：

- 视频完成前，已提交帧可只读查看；首次实际改动时开启重新编辑。
- 服务端接受重新编辑后，将该帧标为 `pending`，旧帧提交版本保留为历史，当前新编辑保存为草稿。
- 已审查帧数随之减少 1；当前视频仍为「审查中」，提示「本帧已修改，需重新提交」。
- 重新提交成功后恢复 `reviewed`；历史记录不覆盖 A，也不丢失上一提交版本。
- 放弃这次重新编辑，则恢复上一有效提交结果和 `reviewed` 状态。放弃草稿不是无条件恢复 A。
- 如果编辑后回到 A，而上一提交版本曾有修改，仍需保留「相对 A 差量为空」的草稿版本并重新提交；否则旧 B 差量无法被清除。
- 视频已点击完成并固定 B 版本后，B 默认只读查看，不在本流程内直接重开。后续返工需另设版本化流程，当前不纳入。

因此「相对 A 没有修改」与「没有待提交编辑」并不总是同一件事。

## 8. 视频级状态与完成

### 8.1 进度来源

```text
total_frames    = 当前任务固定的全部帧数量
reviewed_frames = COUNT(当前有效 frame.review_status == reviewed)
progress        = reviewed_frames / total_frames × 100%
```

`last_viewed_frame`、最大已提交帧号、当前时间轴位置均不能作为进度。任务的全部帧需要独立建档，不能只从「有框的帧」推导总帧数。

### 8.2 三个核心状态

| 状态 | 判定与显示 |
| --- | --- |
| 待审查 `pending` | 尚未有过正式帧提交；仅浏览或保存初始草稿时仍为待审查，可附「有草稿」提示 |
| 审查中 `reviewing` | 已开始正式提交但尚未执行视频完成；包括 `1000/1000`、全部已提交待完成的情况 |
| 已审查 `reviewed` | 所有帧有当前有效提交，且 B 的「完成视频审查」事务成功 |

原说明的 `0 < reviewed_frames < total_frames` 不能覆盖全部已提交但尚未完成的状态。本版明确：此时仍为「审查中」，增加「全部帧已提交，待完成视频审查」提示，不新增第四个核心状态。

**实现补充：** 如果重新编辑导致有效已审查帧数回到 0，已经启动的任务保持「审查中」，不退回「待审查」；使用 `review_started_at` 区分是否曾正式开始。

### 8.3 完成条件与汇总

只有 `reviewed_frames == total_frames`，且无未提交重新编辑或冲突时，才能启用「完成视频审查」。总帧数为 0 或帧集合加载不完整属于异常任务，不能以 `0 == 0` 自动完成。

汇总展示总帧数、已提交帧数、有修改帧数、修改框数，并提供：

- 「继续检查」：关闭汇总，保持审查中，允许继续检查。
- 「完成视频审查」：发起视频级正式完成。

服务端在事务中重新检查所有帧状态及版本；通过后固定 B 视频审查版本，记录 B、完成时间和修改统计，将视频设为 `reviewed`，生成 C 的待确认对象集合。请求失败不改变视频状态；重复请求返回同一个完成版本，不重复创建 C 待办。

已完成视频仍可在左侧「已审查」筛选中查看。B 的审查完成与 C 的最终确认完成使用不同字段和界面状态，不能混用「已审查」表示最终 Ground Truth 已产生。

## 9. 断点续审与浏览位置

### 9.1 单独记录的信息

- `last_viewed_frame`：最后成功展示的帧号。
- `last_accessed_at`：最近访问时间。
- 每帧独立审查状态：决定已提交进度与未审查集合。
- 每帧草稿及更新时间：决定是否可恢复未提交编辑。

浏览位置属于当前审查任务 / 审查员，C 的浏览不覆盖 B 的停留位置。切帧成功后更新位置；尚未成功加载的跳转目标不写为「最后看到」。

### 9.2 重进提示与默认定位

有历史访问记录时提示：

```text
继续上次审查？
上次停留：第 190 帧
已提交：189 / 1000 帧（18.9%）
继续审查将进入：第 190 帧

[查看第1帧]    [继续审查]
```

「继续审查」统一定位到**当前全视频帧号最小的未审查帧**，不简单使用 `last_viewed_frame + 1`。上次位置保留为参考信息。

| 情形 | 继续审查的结果 |
| --- | --- |
| 1～189 已提交，190 未提交 | 打开 190 |
| 1～190 已提交，191 未提交 | 打开 191 |
| 停在 190，但 187 尚未提交且为最早缺口 | 打开 187，并说明它尚未提交 |
| 所有帧已提交，视频尚未完成 | 展示完成汇总，可继续检查或完成视频 |
| 视频已审查 | 只读打开上次有效位置，不恢复成编辑状态 |
| 尚无浏览记录 | 进入最早未审查帧，初始通常为第 1 帧 |

### 9.3 草稿恢复

目标帧存在草稿时提示「第 N 帧存在未提交修改，保存于……」，提供「放弃修改 / 继续编辑」。

- 继续编辑：加载服务端最新有效草稿，并明确标为未提交；恢复框位置、对比和实时统计。
- 放弃修改：清除目标帧草稿；首次审查恢复 A，重新编辑恢复上一次有效提交结果，按第 7.4 节恢复状态。
- 尚未选择时：不自动删除草稿，也不将草稿当成提交结果。

如果上次停留帧有草稿，但最早未审查帧在更前面，继续审查仍定位最早未审查帧；同时提示「第 190 帧另有草稿」并提供定位入口。其他帧草稿继续保留。

**实现补充：** 草稿必须匹配当前 A 版本与帧提交基线。发现不一致时保留草稿并提示冲突，不静默套用到新标注上。

## 10. 草稿自动保存、离页和失败恢复

### 10.1 保存触发与语义

拖动或缩放结束、撤销完成后触发草稿保存。连续操作可合并请求，但必须按版本顺序接受，后到的旧请求不能覆盖较新的编辑。草稿存储表达的是「该帧当前完整的稀疏差量快照」，不是只记录最后一个框。

草稿成功保存后才显示「草稿已保存」，并可显示保存时间。保存过程显示「保存中」，失败显示「保存失败，修改尚未同步」并提供重试。自动保存不增加已审查帧数，不写正式提交时间，不把草稿送给 C。

### 10.2 切帧、切视频与离开页面

**实现补充：** 应用内导航先保存当前待写入编辑，成功后再切换；若失败则留在当前页，保留本地编辑并提供重试或明确放弃操作。该规则只负责保存，不暗中提交。

不要只在关闭窗口事件中保存。正常编辑结束就应写入服务端；关闭、崩溃前尚未成功同步的瞬间编辑无法仅靠服务端自动保存保证恢复。若产品要求这些编辑也尽量恢复，可增加本地持久化缓冲；恢复时检查版本冲突，并明确提示「本地未同步草稿」。本地缓冲属于实现增强，不替代服务端正式保存。

### 10.3 并发与请求乱序

- 每帧保存带预期版本及单调递增的编辑序号，服务端拒绝旧版本覆盖。
- 提交携带幂等键及最新编辑快照；提交过程中冻结同帧编辑，或明确锁定待提交版本。
- 已提交后到达的旧草稿请求不得重新生成该提交前的草稿。
- 完成视频与帧编辑使用同一任务版本校验，避免一端完成、一端继续写入。
- 冲突时保留当前修改，提示重新加载并处理差异，不静默覆盖他人或其他标签页结果。

以上是保证已确认的「保存草稿、断点续审、明确提交」可靠运行的实现补充，具体并发控制方式可由技术栈决定。

## 11. 建议数据结构

本节为实现补充。字段名可调整，但必须表达不可变 A、稳定对象 ID、草稿与正式版本分离、逐帧状态、视频完成版本及 C 决定。所有时间建议使用带时区的标准时间存储；页面根据用户时区展示。

### 11.1 实体关系

```text
Video
 ├─ Frame（完整帧集合，含没有标注框的帧）
 └─ AnnotationVersion A（不可变）
     └─ OriginalAnnotation（稳定 annotation_id）

ReviewTask（绑定 Video、A 版本、B）
 ├─ FrameReview（逐帧状态，指向当前有效提交）
 │   ├─ ReviewDraft（未提交的完整稀疏差量快照）
 │   └─ FrameSubmission（不可变的帧提交历史）
 │       └─ ReviewDelta（本次提交中相对 A 的修改对象）
 └─ ReviewVersion B（视频完成时固定帧提交版本集合）
     └─ ConfirmationTask C
         ├─ ConfirmationDecision（每个修改对象采用 A 或 B）
         └─ FinalAnnotationVersion（最终版本及来源）
```

### 11.2 原始视频、帧与标注

| 实体 | 关键字段 | 约束 |
| --- | --- | --- |
| Video | `video_id, filename, width, height, duration_ms, total_frames` | 媒体信息与任务帧集合一致 |
| Frame | `frame_id, video_id, frame_index, timestamp_ms` | `frame_id` 稳定；本契约 `frame_index` 从 1 开始 |
| AnnotationVersion | `original_version_id, video_id, annotator_id, completed_at` | 作为审查基准后不可变 |
| OriginalAnnotation | `original_version_id, annotation_id, frame_id, class_id, bbox` | 同一 A 版本内 ID 唯一，几何与类别不可由 B 改写 |

界面的 `#004` 仅为短标签。完整 ID 不因排序、缩放、修改或 C 的决定发生变化；即使画面上是「第四个框」，也不能用数组位置进行 A/B 匹配。跨帧轨迹 ID 如需保留，使用独立字段，不能替代帧内对象身份。

```json
{
  "original_version_id": "a_v1",
  "annotation_id": "ann_004",
  "frame_id": "frame_190",
  "class_id": "rare_sperm",
  "bbox": { "x": 512, "y": 336, "w": 24, "h": 24 }
}
```

### 11.3 视频审查任务 ReviewTask

| 字段 | 含义 |
| --- | --- |
| `review_task_id` | 本次 B 审查任务身份 |
| `video_id / original_version_id / reviewer_id` | 绑定视频、A 基准、B |
| `review_status` | pending / reviewing / reviewed |
| `total_frames / reviewed_frames` | 全部帧数 / 当前有效提交帧数 |
| `modified_frame_count / modified_box_count` | 当前有效已提交结果的修改统计 |
| `last_viewed_frame / last_accessed_at` | 浏览位置与最近访问时间 |
| `review_started_at / review_finished_at` | 首次正式提交时间 / 视频完成时间 |
| `completed_review_version_id` | 视频完成后固定的 B 版本，完成前为空 |
| `revision` | 并发控制版本 |

汇总字段可缓存，但权威数据来自帧记录和对应当前有效提交。重新编辑失效的旧提交不计入当前有效汇总；历史统计如需展示必须另行命名。

### 11.4 帧审查 FrameReview

| 字段 | 含义 |
| --- | --- |
| `review_task_id / frame_id` | 唯一键 |
| `review_status` | pending / reviewed |
| `current_submission_id` | 当前有效提交；尚未提交或重新编辑时为空 |
| `previous_submission_id` | 重新编辑时保存可恢复的上次提交引用 |
| `reviewed_by / reviewed_at` | 当前有效提交人和时间；无有效提交时为空 |
| `original_box_count / modified_box_count` | 原框数 / 当前有效提交的修改数 |
| `draft_exists / draft_updated_at` | 草稿元信息，可由草稿表派生 |
| `revision` | 帧状态版本 |

```json
{
  "review_task_id": "review_001",
  "frame_id": "frame_190",
  "review_status": "reviewed",
  "current_submission_id": "submission_190_v1",
  "previous_submission_id": null,
  "reviewed_by": "B",
  "reviewed_at": "2026-09-26T08:15:00Z",
  "original_box_count": 8,
  "modified_box_count": 1,
  "draft_exists": false,
  "draft_updated_at": null,
  "revision": 5
}
```

### 11.5 草稿 ReviewDraft

```json
{
  "review_task_id": "review_001",
  "frame_id": "frame_190",
  "original_version_id": "a_v1",
  "base_submission_id": null,
  "reviewer_id": "B",
  "draft_revision": 3,
  "client_edit_seq": 12,
  "updated_at": "2026-09-26T08:14:00Z",
  "deltas": [
    {
      "annotation_id": "ann_004",
      "reviewed_bbox": { "x": 520, "y": 338, "w": 26, "h": 26 }
    }
  ]
}
```

`deltas` 是该草稿版本完整的相对 A 差量集合。集合中不存在的对象使用 A；服务端接受新的空集合时必须清除旧草稿差量，不能把空集合理解为「无需更新」。

草稿是否有待提交变化按相对于编辑基线的结果判断：首次审查基线为 A，重新编辑基线为上一提交结果。因此重新编辑时 `deltas=[]` 仍可能表示待提交的「恢复为 A」操作。

### 11.6 帧提交与正式 ReviewDelta

FrameSubmission 保存不可变提交头：`submission_id、review_task_id、frame_id、original_version_id、submitted_by、submitted_at、original_box_count、modified_box_count`。ReviewDelta 挂在明确的 `submission_id` 下，保存每个修改对象的最终几何及差异。

```json
{
  "submission_id": "submission_190_v1",
  "annotation_id": "ann_004",
  "original_version_id": "a_v1",
  "reviewer_id": "B",
  "original_bbox": { "x": 512, "y": 336, "w": 24, "h": 24 },
  "reviewed_bbox": { "x": 520, "y": 338, "w": 26, "h": 26 },
  "change_type": "position_and_size",
  "iou": 0.39111111111111113,
  "delta_cx": 9,
  "delta_cy": 3,
  "center_shift_px": 9.486832980505138,
  "delta_w": 2,
  "delta_h": 2
}
```

`original_bbox` 可以通过不可变 A 版本引用获取，也可冗余保存快照；如冗余存储，写入时必须验证它与 A 一致。指标由服务端复算，客户端值仅用于实时预览。

一个对象不管拖动多少次，在同一帧提交版本中最多只有一条有效差量。未修改对象没有 ReviewDelta 行。读取完整 B 结果时按 `annotation_id` 合并 A 与该提交的差量。

### 11.7 视频完成版本 ReviewVersion

保存 `review_version_id、review_task_id、original_version_id、reviewer_id、completed_at`，并固定每个帧的 `submission_id`，保存完成时修改帧数和修改框数。

C 读取该固定版本，不读取 B 当前可变工作区，也不能取历史所有差量的并集。否则同一对象多次提交会被误当成多个待确认事项。

### 11.8 C 的决定与最终结果

```json
{
  "confirmation_task_id": "confirm_001",
  "review_version_id": "b_v1",
  "annotation_id": "ann_004",
  "frame_id": "frame_190",
  "decision": "use_b",
  "confirmed_by": "C",
  "confirmed_at": "2026-09-26T09:00:00Z",
  "revision": 1
}
```

`decision` 建议为 `pending / use_a / use_b`。每个确认任务内，同一对象只有一个当前有效决定；修改决定保留历史。未修改对象不需要 C 决定行，最终自动沿用 A。

最终版本保存 `final_version_id、original_version_id、review_version_id、confirmation_task_id、finalized_at`，以及每个对象的来源：未修改自动沿用 A、C 选择 A、C 选择 B。可直接保存几何或通过不可变引用解析，但必须能稳定重建最终结果与追溯来源。

## 12. 数据读取、写入与接口契约

本节接口名是逻辑操作名称，不限定 URL 或通信协议。

| 操作 | 主要输入 | 权威读写与输出 |
| --- | --- | --- |
| 获取视频列表 | 状态筛选、分页、任务范围 | 读取已完成原始标注的视频及 ReviewTask，返回状态、进度、停留位置、草稿提示 |
| 打开审查任务 | task_id | 返回 A 版本、完整帧清单、帧状态摘要、首个未审查帧、停留位置、草稿摘要 |
| 加载当前帧 | task_id、frame_id | 返回帧图像定位、A 对象、当前提交、草稿元信息、权限及版本 |
| 更新浏览位置 | task_id、成功展示的 frame_index | 只更新 last_viewed_frame、last_accessed_at |
| 自动保存草稿 | task_id、frame_id、A 版本、预期帧/草稿版本、编辑序号、完整稀疏差量 | 校验并保存草稿，返回服务端版本、保存时间；若开启重新编辑，一并更新帧状态及进度 |
| 放弃草稿 | task_id、frame_id、预期草稿版本 | 原子清除草稿，按编辑基线恢复 A 或上一有效提交；返回帧状态和最新进度 |
| 提交本帧 | task_id、frame_id、最新有效快照、预期版本、幂等键 | 原子创建帧提交、写正式差量、变更状态、清草稿，返回统计及下个未审查帧 |
| 完成视频审查 | task_id、预期任务版本、幂等键 | 验证全帧，固定 B 版本、修改视频状态、创建一次 C 确认任务 |
| 获取 C 待确认列表 | confirmation_task_id、状态筛选、分页 | 只取固定 B 版本中的修改对象，连同 A/B 几何、同帧图像、指标和已有决定返回 |
| 保存 C 决定 | task_id、annotation_id、use_a/use_b、预期版本 | 绑定固定 A/B 版本写对象级决定，返回确认进度 |
| 完成 C 确认 | confirmation_task_id、预期版本、幂等键 | 验证无待决定对象，固定最终结果及来源 |

### 12.1 前端、服务端和存储职责

前端负责展示当前编辑快照、选中联动、拖动操作、即时指标和保存反馈。服务端负责权限、对象集合、版本、几何合法性、业务状态、幂等、事务及正式指标计算。存储层分别保留 A、草稿、帧提交历史、固定 B 版本、C 决定和最终版本。

服务端从认证身份确定 B/C，不直接信任客户端任意填入的用户 ID。前端隐藏「新增」「删除」不足以保证权限，服务端同样必须拒绝新增对象、删除对象和修改类别。

### 12.2 一次修改的数据流

```text
B 拖动 ann_004
  → 前端当前帧快照变化
  → 主画面、对比图、表格、实时统计同步变化
  → 保存草稿请求
  → 服务端验证版本与几何，保存 ReviewDraft
  → 页面显示「草稿已保存」，本帧仍未提交
  → B 点击「提交本帧」
  → 服务端复算差量，提交事务成功
  → FrameSubmission / ReviewDelta 固定
  → FrameReview 设为 reviewed，对应草稿清除
  → 视频已提交统计更新
  → 前端跳转下一未审查帧
```

### 12.3 事务与不变量

1. A 在审查期间和最终确认后均可原样读取。
2. 同一 A 基准下，A、B、最终结果的对象集合与类别一致，允许变化的只有已有框几何。
3. 帧已提交状态与有效提交记录必须一致；不能先标 reviewed 再异步尝试保存结果。
4. 当前视频进度始终等于有效 reviewed 帧数，不因重复请求或乱序浏览增加。
5. 正式完成的 B 版本中每一帧都有有效提交，即使没有对象差量。
6. 当前 C 待确认对象数等于固定 B 版本中的修改对象数。
7. 最终结果只解析固定的 A/B 版本与 C 决定，草稿永不进入最终结果。

## 13. 第三人 C 的对比确认

### 13.1 已确认的业务范围

C 对比 A 原始标注与 B 审查修改结果，决定最终采用哪一个。C 的工作集合只包含 B 最终审查版本中修改的对象。

例如：视频共有 1000 帧、7642 个原始对象，B 在 86 帧中修改 218 个对象，C 的待确认总数为 218。未修改的 7424 个对象自动沿用 A，不要求 C 再检查一遍。

以下交互和状态为满足上述目标的建议实现；原对话没有明确 C 页面的具体布局、批量确认或复核返工机制。

### 13.2 建议页面与逐对象操作

| 区域 | 内容和用途 |
| --- | --- |
| 任务头部 | 视频名称、A/B 版本、B 完成时间、待确认总数、已决定数 |
| 修改对象列表 | 帧号、对象 ID、修改类型、IoU、中心位移、尺寸变化、决定状态 |
| A/B 对照 | 同一帧图像、相同比例与上下文，清楚标明原标注 A 与审查版本 B |
| 决定操作 | 「采用原标注 A」「采用审查版本 B」 |
| 导航 | 上一个、下一个待确认对象；只导航不代替选择 |
| 最终完成 | 所有修改对象有决定后启用「完成对比确认」 |

C 点击采用 A：记录 `use_a`，最终几何使用 A。点击采用 B：记录 `use_b`，最终几何使用 B 的固定提交结果。保存成功后更新确认进度，可进入下一个待确认对象；失败留在当前对象，不增加进度。

每个对象单独选择，不默认整帧采用同一版本，也不以 IoU 自动决定。当前不加入批量采用、再次拖框、填写必填原因、退回 B 等未经确认的功能。

### 13.3 C 的状态与恢复：实现补充

| 层级 | 状态 | 定义 |
| --- | --- | --- |
| 对象 | pending | C 尚未保存 A/B 选择 |
| 对象 | use_a / use_b | 已保存明确选择 |
| 确认任务 | pending | 尚未做决定，未最终完成 |
| 确认任务 | confirming | 已做决定，尚未最终完成；包括全部选择但未点完成 |
| 确认任务 | confirmed | C 已完成确认并固定最终版本 |

按对象保存决定和浏览位置，重进时默认定位首个 pending 对象。C 正式完成前可修改选择，保留决定历史；完成后固定最终版本。并发保护和幂等规则与 B 一致。

如果 B 没有修改任何对象，C 页面显示「无修改项，全部沿用 A」，不生成空对象待办。**实现补充：** 为保持明确的最终版本产生节点，仍允许 C 点击「完成对比确认」形成最终版本，记录人工完成动作；不要求逐框确认。是否将零修改任务自动完成，是后续可选策略，当前默认不自动执行。

### 13.4 最终标注生成

```text
对于 A 中的每个 annotation_id：
  固定 B 版本没有差量 → 最终采用 A，来源为 unchanged_a
  固定 B 版本有差量：
    C = use_a        → 最终采用 A，来源为 confirmed_a
    C = use_b        → 最终采用 B，来源为 confirmed_b
    C = pending      → 不允许完成最终版本
```

最终输出的框数与 A 相同，ID、帧归属、类别保持不变。采纳 B 也不删除 A；采纳 A 也不删除 B 的审查记录。最终版本需能追溯到 A、B、C 及其时间和版本。

## 14. 统计口径与显示约定

| 指标 | 计算来源 | 草稿是否影响 |
| --- | --- | --- |
| 当前帧总框数 | A 当前帧对象数 | 否 |
| 当前帧修改框数 | 当前显示的有效几何与 A 比较 | 是 |
| 当前帧未修改框数 | 总框数 − 当前帧修改框数 | 是 |
| 当前帧平均 IoU | 当前帧修改对象的 IoU 算术平均 | 是 |
| 当前帧最大中心位移 | 当前帧修改对象的中心位移最大值 | 是 |
| 视频已提交帧数 | 当前有效 reviewed 帧数 | 草稿不增加；重新编辑可使旧提交失效 |
| 视频修改帧数 | 当前有效提交中至少有 1 个差量的帧数 | 否 |
| 视频修改框数 | 当前有效提交差量行数总和 | 否 |
| C 待确认总数 | 固定 B 版本的差量对象总数 | 否 |
| C 已决定数 | 当前 use_a 或 use_b 的对象数 | 否 |

视频完成后的汇总取固定 B 版本，之后 C 是否采纳 B 不反向改写 B 的修改统计。若未来增加视频平均 IoU，应对该版本全部修改对象求平均，不能不加权地平均各帧平均值。

本版进度建议统一显示一位小数，例如 `189/1000 = 18.9%`，避免同页同时出现 18.9% 和 19% 造成误解。数值 0 与无可用样本的 `—` 必须区分：修改框的中心位移可以为 0，而无修改框时最大位移为 `—`。

## 15. 空态、异常和操作反馈

| 场景 | 页面反馈 | 数据行为 |
| --- | --- | --- |
| 没有可审查视频 | 显示「暂无已完成标注的待审查视频」 | 不创建空任务 |
| 筛选无结果 | 显示「当前筛选下暂无视频」 | 不改变已有任务 |
| 当前帧没有框 | 画面显示、表格空态，允许提交本帧 | 提交记录框数和修改数均为 0 |
| 图像或 A 加载失败 | 显示加载失败及重试，禁用编辑和提交 | 不标记为已审查 |
| 草稿保存中 | 显示保存中 | 不提前声称持久化成功 |
| 草稿保存失败 | 显示未同步及重试 | 保留当前编辑，不推进进度 |
| 提交失败 | 提示原因，保留当前帧及编辑 | 不跳转，不计数 |
| 视频完成时仍有未提交帧 | 提示剩余帧数，提供返回未审查帧入口 | 不设置 reviewed，不创建完成版本 |
| 多窗口编辑冲突 | 提示版本变化，保留本地编辑供处理 | 拒绝旧版本覆盖 |
| 请求返回顺序错乱 | 不让旧响应覆盖当前帧画面或版本 | 按 task/frame/revision 校验响应 |
| A 基准发生变化 | 提示基准不一致，停止自动合并 | 保留旧 A 和草稿引用，禁止套用到新 A |
| 重复提交 / 完成请求 | 返回已成功的同一结果 | 不重复计数、生成版本或创建 C 待办 |

仅显示与实际状态相符的反馈。例如草稿失败时不能显示「已保存」，视频完成失败时不能显示「已审查」。

| AC-30 | C 对同帧不同对象分别采用 A 和 B | 按对象保存并正确生成最终结果，不强制整帧同选 |
| AC-31 | C 尚有一个 pending 对象 | 不能完成最终版本 |
| AC-32 | C 全部决定并完成确认 | 最终版本可追溯到 A/B/C，原始框数、ID、类别保持一致 |
| AC-33 | B 全视频无修改 | C 显示 0 个修改项，按明确的完成动作形成全部沿用 A 的最终版本 |
| AC-34 | B 已完成视频后再次打开 | 只读查看固定结果，不能污染 C 正在处理的版本 |

## 17. 实现补充与范围边界清单

为避免把补全方案误认为原始需求，本版新增的实施约定集中列出如下：

| 项目 | 本版默认方案 |
| --- | --- |
| 全部提交但未完成的视频 | 仍为审查中，附待完成提示 |
| 已提交帧再次修改 | 旧提交留历史，当前帧转 pending；放弃可恢复旧提交 |
| B 视频完成后编辑 | 当前流程只读，不直接重开 |
| 草稿精度与坐标范围 | 同一原始像素坐标系、统一规范化、服务端校验 |
| 对比裁剪 | A/B 使用相同上下文和比例 |
| 提交后跳转 | 向后找未审查帧，找不到则回到最早缺口 |
| 保存失败和并发 | 保留编辑、明确提示，使用版本校验和幂等 |
| 空帧 | 仍逐帧显式提交 |
| C 具体状态与收尾 | 对象级 A/B 选择，全部决定后显式完成 |
| C 零修改任务 | 无逐项待办，显式完成形成沿用 A 的最终版本 |
| 数据结构和接口 | 为可追溯性提供的建议契约，不限定技术栈 |

不纳入本次范围：新增或删除框、类别修改、人工问题标记、必填修改原因、检测评估指标、按 IoU 自动采纳、C 重新画框、批量采纳、重做、跨会话撤销栈、多人同时编辑同一任务、完成后的返工审批流程。并发防覆盖是数据保护要求，不代表引入多人协同编辑功能。

本文定义的核心闭环是：A 固定基准 → B 必要时编辑并保存草稿 → 每帧显式提交 → 全视频显式完成 → C 对修改对象选择 A/B → 固定可追溯的最终标注版本。
