# 审查模式：后端数据与接口设计

版本：1.0（面向现有项目的目标设计）  
日期：2026-09-26  
技术基线：现有 FastAPI / Pydantic / Python sqlite3 / SQLite / 本地媒体存储  
用途：指导后端改造、前端联调、数据迁移和验收。

> 本文区分“现状”与“目标”。目标字段、接口及事务规则尚未由本文实现。此次工作只读取源码和数据库结构/汇总，未运行应用启动、数据库迁移或修改业务数据。原型确定交互意图，需求说明与最终审查修正清单约束业务语义；不能直接照搬 HTML 的内存状态和保存顺序。

## 1. 设计结论与范围

保留现有单 FastAPI 服务、SQLite 数据库、媒体目录和认证方式，在现有 review/confirmation 模块上改造。优先修复源数据完整性、帧提交不可变记录、草稿分离、显式视频完成和原子事务，不新建独立审查后端，不引入另一套媒体编号。

覆盖以下完整流程：

```text
已有人工标注 + A 接受的 AI Tracking 结果
    → A 显式完成全视频标注
    → 冻结 A 基准 + 创建待审查任务
    → B 领取、浏览、必要时编辑已有框
    → 草稿自动保存 / 恢复 / 放弃
    → 逐帧显式提交
    → B 显式完成视频审查，固定 B 版本
    → C 只对 B 修改对象选择 A/B
    → C 显式完成确认，固定最终 F 版本
    → 可追溯读取与训练数据导出
```

本期不新增/删除框、不修改类别、不要求修改原因，不引入“标记问题→阻塞/退回”工作流，不计算 Precision/Recall。历史 issues 表保留用于历史读取，不沿用其控制新任务状态的逻辑。

### 1.1 目标设计中的新增约定

以下属于为开发明确的实施约定，并非此前对话逐项确认的产品功能：

- 保留现有后端 0 起始帧号、`xyxy` 原始像素坐标；前端展示转换。
- 坐标统一为 0.001 px 精度；合法旧整数坐标保持原数值，不乘以1000。
- 采用单工作组部署，增加简单角色授权和任务领取权限；不引入多租户/复杂项目管理。
- 默认 A、B、C 为不同用户；测试环境若需一人演示应显式启用配置并记录，不能成为生产默认。
- 每个新 A 基准对应一个本期 B 任务、每个固定 B 版本对应一个 C 任务；完成后的返工需另建版本，暂不在本期直接开放。
- 使用新契约版本标识与迁移门禁，旧异常数据不自动修正成“已完成”。

### 2.3 当前数据库只读检查结果

检查时存在2个media_revision、2个A基准、2个in_progress审查任务及20条unreviewed帧；frame_submissions、review_versions、review_changes、confirmation_sessions、final_versions均为0条。

两个基准分别只覆盖0～9，共10帧，而对应源视频为678帧和12帧。没有显式empty帧。**这两个任务不能直接继续作为完整视频审查任务。** 迁移时保留原记录、标记旧任务只读且待重新确认A；不得把缺失668帧/2帧自动填为空帧。A重新完成全帧覆盖后创建新基准和任务。

该结论针对检查时数据；执行迁移前必须重新扫描，不能把本次数量硬编码进迁移脚本。

## 3. 业务不变量

1. A不可变。B草稿、提交、C决定都不得写入A、manual seed或Tracking结果文件。
2. 同一A基准内，对象身份为`(baselineId, frameIndex, objectId)`；B/F的对象集合与类别必须与A完全一致。
3. 每个源视频帧都有A覆盖记录和B审查状态，含零对象帧。
4. 浏览游标不改变审查状态；保存草稿不等于提交；帧全部提交不自动冻结B。
5. 当前有效进度仅统计`review_frames.state='submitted'`；最近成功提交引用存在不代表当前没有新草稿。
6. 每次成功提交都是可重建的不可变记录。失败不能覆盖上一成功提交，也不能因随后放弃草稿变成成功提交。
7. B冻结必须绑定每帧唯一有效submission；C只能看已固定B的净变化对象。
8. C采纳A或B不删除任何历史版本；F保留来源。
9. 任一业务写入失败，所有相关状态、指针、计数、事件和幂等记录一起回滚。
10. 完成后的版本只读，但帧浏览、选择对象、对比图和下载仍允许在权限范围内使用。

## 4. 服务结构与文件边界

建议按现有文件演进：

```text
review_routes.py / review_models.py（新增）
    认证、输入校验、响应模型、错误映射
        ↓
review_service.py（新增）
    授权、幂等、事务编排、状态转换
        ↓
review_repository.py
    只执行使用传入conn的SQL，不在子步骤自行commit
        ↔ review_geometry.py（新增：规范化、差量、IoU）
        ↔ annotation_completion_service.py（新增：A的源数据汇总与冻结）
        ↔ media访问/解码服务（复用main.py，逐步提取）
        ↓
SQLite：A/草稿/提交/B/C/F/游标/幂等
文件存储：视频、可变A工作区、图像缓存、导出包
```

数据库是审查业务的权威来源；文件仍是媒体和A工作区来源。浏览器缓存只提高体验，不作为提交或完成依据。B操作不依赖GPU，继续使用现有单进程Tracking队列，不因B拖动启动SAM3。

迁移从应用导入阶段移出：先基础用户表，再有序迁移，再注册/开放业务；禁止导入`main.py`就执行不可控升级。未来命令示例为`python -m app.migrations upgrade`，该命令需开发实现，并非现有可用命令。

## 5. 坐标、帧号、时间和身份契约

### 5.1 帧号

- 所有数据库和API继续使用`frameIndex`，整数，0起始，合法范围`0 <= i < media.frameCount`。
- UI“第190帧”对应`frameIndex=189`。前端统一在展示/输入边界±1，不在每个API调用里各自猜测。
- 帧ID不依赖播放时间。优先复用`GET /api/track/frame/{mediaId}/{frameIndex}`的原始帧读取。
- CFR可用`frameIndex/fps`显示参考时间；若支持VFR，增加解码PTS索引并返回真实timestampMs。不得对所有视频使用固定33.3秒。

### 5.2 框坐标

本项目已有API和Tracking以`[x1,y1,x2,y2]`原始像素传输，本期继续沿用。响应明确给出`bboxFormat='xyxy'`、`coordinateUnit='px'`。

```text
原型 x/y/w/h → API [x, y, x+w, y+h]
API [x1,y1,x2,y2] → 原型 x=x1, y=y1, w=x2-x1, h=y2-y1
```

允许数值小数，统一规范化为0.001 px：Python用十进制字符串构造Decimal并按ROUND_HALF_UP舍入，拒绝bool、NaN、Infinity和数值字符串。规范化后再次校验边界和正宽高。JSON数值可用整数或小数形式，内容hash采用统一十进制定点字符串，见5.4。

约束：`0 <= x1 < x2 <= width`，`0 <= y1 < y2 <= height`。坐标为连续区间，面积不加1。不静默裁剪越界请求，不让`int()`截断新数据。

仓库`canonical_frames_json`注释称milli-pixel ints，但前端、seed JSON和测试生成脚本实际使用原始像素。**本设计定义API始终为px，历史值不乘/除1000。** 历史来源若真为另一单位，需按来源元数据单独转换，不能凭注释批量改库。

旧人工标注百分比bbox只在A汇总适配器中按源width/height转换一次。A基准冻结后不再使用百分比或屏幕坐标。

### 5.3 稳定身份与类别

- `mediaId`：现有媒体目录身份，不能用文件显示名称或文件内容hash代替。
- `mediaRevisionId`：绑定该资产的不可变视频内容版本。
- `objectId`：沿用既有正整数Tracking实体ID，同一帧唯一，可跨帧相同；不按数组下标重编号。
- `annotationId`：在A冻结时生成，例如`ann_<baselineId>_f189_o4`，随B/F继承。
- `classKey`：继承A的明确类别；对象显示名称（例如带编号的rare sperm 4）不是类别。未配置类别的旧单类数据按显式迁移映射到sperm，不能把所有新类别都写死成sperm。

### 5.4 标准化与哈希

按frameIndex、objectId排序；固定字段顺序，UTF-8，无无关空格。bbox内部hash表示用精确3位小数字符串，例如`"512.000"`；API仍返回数值。

新增`canonical_format_version=2`，旧hash保留原算法标识，不重算后冒充原版本未变。内容hash包括媒体版本、A基准、坐标单位/格式、全帧coverage、对象ID/annotationId/classKey和标准化几何。审查者/时间不影响几何内容hash，另作审计。

B/F hash均应覆盖空帧。HTTP幂等请求hash包含路径、行为及标准化请求体，不能只hash框坐标。

## 6. 目标数据结构

保留既有表名。以下为目标契约：列出新增表全部业务字段、既有表需新增或改义的字段；未列出的现有主键/创建时间等继续保留。SQLite JSON字段存UTF-8 TEXT；跨行不变量由服务层在同一事务内验证。

### 6.1 媒体与权限

**新增`media_assets`**：

| 字段 | 类型/约束 | 说明 |
| --- | --- | --- |
| media_id | TEXT PK | 既有mediaId |
| original_name | TEXT NOT NULL | 原文件名，不包含UI重名后缀 |
| storage_relpath | TEXT NOT NULL | 受存储根约束的相对路径，不信任客户端绝对路径 |
| created_by | INTEGER FK users | 新数据必填；旧数据无法可靠识别时迁移待确认 |
| created_at | TEXT NOT NULL | UTC |
| archived_at | TEXT NULL | 软归档，不物理删除已有版本依赖的媒体 |

**调整`media_revisions`**：继续保留id/media_id/sha256/file_size/width/height/fps/frame_count；media_id关联media_assets。取消sha256单列全局唯一，改为`UNIQUE(media_id, sha256)`；不同mediaId可引用相同内容。新id用UUID前缀，不再只取hash前16位。历史id保留，避免断开已有外键。新增`timing_mode='cfr'|'pts'`、`canonical_format_version`，必要时媒体旁保存不可变PTS索引。

**新增`workflow_user_roles`**：`user_id INTEGER FK users`、`role TEXT CHECK IN ('annotator','reviewer','confirmer','admin')`、`granted_at TEXT`；PK(user_id,role)。注册默认不授予管理权限；首次管理员由部署命令配置，普通业务API不能自行提权。角色只是最小能力授权，仍须核验任务领取人与媒体源写入权限。

### 6.2 A基准与全帧覆盖

`annotation_baselines`保留id、media_revision_id、submitted_by、snapshot_hash、frame_count、object_count、created_at。新增：

- `source_revision TEXT NOT NULL`：冻结时的A工作区来源摘要。
- `source_manifest_json TEXT NOT NULL`：workspace/Tracking/seed来源及文件hash，不保存机器绝对路径。
- `canonical_format_version INTEGER NOT NULL`、`workflow_model_version INTEGER NOT NULL`。
- `validation_state TEXT`：`valid`或`legacy_incomplete`；仅valid可新建v2任务。

`baseline_frames`保持PK(baseline_id,frame_index)。字段coverage严格为`objects|empty`；`objects_json`包含`annotationId, objectId, classKey, bbox`；新增timestamp_ms（可空）。coverage=empty时objects必须为空；objects时至少1个对象。

基准frame_count等于媒体真实N，baseline_frames必须精确覆盖0…N−1。缺失表示未知，绝不视为empty。为保持当前文件结构，本期可继续JSON存每帧A对象，不必立即拆成对象表；唯一性、边界和类别校验必须在冻结前完成。

### 6.3 B任务 review_sessions

保留`state`已有英文映射：`pending / in_progress / reviewed`，UI分别显示待审查/审查中/已审查。历史blocked/returned只在旧记录读取兼容，新任务不产生。

新增/明确字段：

| 字段 | 目标含义 |
| --- | --- |
| reviewer_id | 领取人；领取不自动进入in_progress |
| revision | 任务业务版本，所有改变任务业务状态/帧状态/草稿的成功写入递增；游标不增加 |
| claimed_at / started_at / finished_at | 领取、首次有效帧提交、视频正式完成时间 |
| completed_review_version_id | 完成B版本引用，完成前NULL |
| workflow_model_version | 旧1，新2；v1默认只读待迁移判断 |
| validation_state | valid / legacy_read_only / needs_baseline_rebuild |
| frame_count | 固定等于A与媒体N，不接受客户端修改 |

提交数、修改帧数和修改对象数优先查询聚合。已有changed_count若保留缓存，语义固定为“当前有效已提交中的净修改帧数”，与事实表同事务更新。禁止按点击次数累加。

约束：新v2任务`UNIQUE(baseline_id)`，可用带workflow_model_version=2条件的部分唯一索引保留历史多个任务。已存在v2任务时创建接口返回已有任务，不再创建第二个。

### 6.4 帧状态、草稿、成功提交

**`review_frames`目标字段**：

| 字段 | 类型/规则 |
| --- | --- |
| session_id / frame_index | 复合PK；必须存在于任务A帧集合 |
| state | `unreviewed / submitted`；旧draft迁为unreviewed+草稿 |
| frame_revision | INTEGER NOT NULL，帧级CAS版本 |
| submission_id | 最近一次成功提交引用；重新编辑时仍保留，用于放弃恢复 |
| updated_at | UTC最近有效变更时间 |

`submission_id`存在但state=unreviewed表示有新未提交编辑。进度仅按state=submitted计，不按指针是否非空计。旧`patch_json`停止作为v2权威写入字段，迁移后只用于历史兼容。

**新增`review_frame_drafts`**：

| 字段 | 类型/约束 | 说明 |
| --- | --- | --- |
| session_id / frame_index | PK，复合FK review_frames | 一帧最多一个当前草稿 |
| base_submission_id | FK frame_submissions NULL | 首次审查NULL，重新编辑指向上一成功提交 |
| patch_json | TEXT NOT NULL，允许`[]` | 完整的、相对A的稀疏差量快照 |
| payload_hash | TEXT NOT NULL | 标准化草稿内容摘要 |
| updated_by | INTEGER FK users NOT NULL | B |
| updated_at | TEXT NOT NULL | UTC |

草稿存在即hasDraft=true，通过联表派生，不另存易失配布尔列。

**扩展`frame_submissions`**：保留id/session_id/frame_index/revision/net_change_count/reviewer_id/submitted_at；新增`baseline_id`、`patch_json NOT NULL`、`payload_hash NOT NULL`、`canonical_format_version`。约束`UNIQUE(session_id,frame_index,revision)`。每条成功提交不可变，即便patch=[]也有提交记录。旧记录缺少内容时不能捏造历史patch，按第15节迁移。

提交patch元素固定为：

```json
{"annotationId":"ann_abl_example_f189_o4","objectId":4,"bbox":[520,338,546,364]}
```

客户端只提交已有对象的新几何。patch不包含classKey，不支持add/remove操作。服务端根据A生成annotationId并核验客户端若传入的值一致；正式请求推荐只传objectId+bbox以减少冗余。

**空patch与无草稿不同：** 上一次提交改过框，本次希望恢复为A，则新草稿patch=[]仍必须保留，因为它相对于上一成功B有变化；提交成功后才替换有效版本。只有新有效几何等于编辑基线，才消除草稿。

### 6.5 固定B版本与修改对象

扩展`review_versions`：`completed_by INTEGER FK users`、`completed_at TEXT`、`frame_count`、`modified_frame_count`、`modified_box_count`、`canonical_format_version`；`UNIQUE(session_id)`对v2生效。baseline_id与任务基准必须一致。

**新增`review_version_frames`**：PK(review_version_id,frame_index)，`submission_id FK frame_submissions NOT NULL`、`coverage`、`content_hash`。固定B依靠A与每帧不可变提交引用重建，不读取后续可变草稿。N条映射包含空帧。

`review_changes`保留已有几何/指标字段；必须填写`frame_submission_id`，新增/明确`change_type`及`delta_center_x/delta_center_y`。约束`UNIQUE(review_version_id,frame_index,object_id)`，防止历史多次提交产生重复待确认项。

`dx/dy`保留旧含义：左上角位移；中心位移分量用新字段，不能混用。before/after bbox、classKey来源均绑定A与对应submission。

### 6.6 C任务、决定事件和F版本

`confirmation_sessions`保持`pending / in_progress / confirmed`；新增claimed_at/started_at/finished_at、completed_final_version_id、workflow_model_version。`UNIQUE(review_version_id)`。领取绑定C，首次决定再进入in_progress；零修改任务可直接显式finalize。

保留`decision_events`追加历史、`decision_heads`当前指针模式。新增`decision_heads.revision INTEGER NOT NULL`，每个对象独立CAS；event内的revision定义为对象决定版本，另加session_revision记录任务版本。choice仅A/B，note可保留兼容但不要求填写，也不新增原因表单。

`decision_heads`需核验change确属confirmation关联的固定B版本，不能仅靠外键确保“存在”。历史事件不可覆盖；完成后不能改head。

`final_versions`新增/明确`UNIQUE(confirmation_id)`、canonical_format_version。新增**`final_frames`**：PK(final_version_id,frame_index)，coverage、timestamp_ms、content_hash。`final_frame_objects`以复合FK关联final_frames，新增class_key，保留bbox/annotation_id/resolution/change_id/baseline_bbox/adopted_bbox。

resolution保持现有：`unchanged / kept_a / adopted_b`。F对象数和类别与A一致，空帧通过final_frames保留；不能从有对象的结果表推测全视频帧集合。

### 6.7 游标与幂等

`resume_cursors`保留PK(user_id,stage,session_id)、frame_index、change_id、updated_at；新增`revision INTEGER NOT NULL DEFAULT 0`。stage严格review/confirmation，cursor更新只改游标，不改帧或任务版本。

**新增`api_idempotency_requests`**：

| 字段 | 类型/规则 |
| --- | --- |
| actor_id / operation / resource_key / idempotency_key | 复合PK；operation含HTTP方法和规范路径 |
| request_hash | 标准化请求摘要 |
| response_status / response_json | 成功事务对应响应 |
| created_at / expires_at | UTC；建议保留至少7天 |

幂等记录与业务变化同事务提交。相同key不同请求体返回409；相同key同请求体返回原成功结果，不再执行。到期后仍通过“每任务唯一完成版本”等数据库约束防止重复完成。失败事务不写入成功幂等记录。

### 6.8 必要索引与一致性约束

新增索引：review_frames(session_id,state,frame_index)、drafts(session_id,updated_at)、submissions(session_id,frame_index,revision)、changes(review_version_id,frame_index,object_id)、decision_heads(confirmation_id,choice)、baselines(media_revision_id,created_at)、media_assets(original_name)。

保留所有外键检查，不因所谓“外键race”关闭。不可变A/B/F及其依赖改为RESTRICT删除或应用级归档；禁止现有媒体DELETE接口绕过引用保护删除视频目录。历史CASCADE约束需在迁移重建表时审慎调整，不能借迁移清空历史。

## 7. 状态机与统计口径

### 7.1 视频任务

```text
pending（可已领取、可有草稿）
    -- 第一次成功提交帧 --> in_progress
in_progress（含N/N全部提交但未完成）
    -- 显式freeze且全部当前帧submitted --> reviewed
reviewed：不可再编辑，读取固定B版本
```

领取、打开视频、保存游标和保存草稿不把任务变成in_progress。已经正式开始的任务即使因重新编辑变为0个有效提交，也保持in_progress。

### 7.2 帧与草稿

| 当前状态 | 操作 | 成功后的状态 |
| --- | --- | --- |
| unreviewed，无历史提交、无草稿 | 保存相对A有变化的patch | unreviewed + draft，baseSubmissionId=NULL |
| unreviewed，无历史提交 | 保存有效几何等于A的patch | unreviewed，无草稿 |
| submitted，提交S1 | 保存与S1不同的有效几何 | unreviewed + draft，submission_id仍指S1 |
| unreviewed，有S1与草稿 | 保存几何恢复为S1 | submitted，无草稿，沿用S1 |
| unreviewed，有草稿 | discard | 无S1则恢复A并unreviewed；有S1则恢复S1并submitted |
| unreviewed，无草稿或有草稿 | submit成功 | 新不可变S2、submitted、清草稿 |
| submitted，无新编辑 | 重复submit同一有效内容 | 返回当前提交，不增历史、不增加计数 |
| 任意可编辑状态 | 写入失败 | 原事务状态不变，不更新成功基线 |

“恢复为A”只表示A/B净差量为空，是否需要重新提交取决于与最近成功提交相比是否变化。B1改过框、草稿恢复为A时必须保留空patch草稿；成功submit后新提交S2.patch=[]。

### 7.3 C任务

`pending`→首次决定成功→`in_progress`→C显式finalize→`confirmed`。领取不自动作决定；0个修改项时pending可以直接finalize。完成前可改决定，历史事件追加；完成后只读。

### 7.4 统计

- `submittedFrames`：state=submitted的帧数。
- `unsubmittedFrames=N-submittedFrames`，包含有草稿与未看过的帧。
- `draftFrames`：草稿表对应帧数。
- `modifiedFrames/modifiedBoxes`：仅对submitted帧所引用submission的标准化净差量计算。
- 当前帧指标：当前有效草稿优先，否则最近成功提交，否则A；客户端拖动预览与后端保存确认可短暂不同，保存后采用后端值。
- `firstUnsubmittedFrameIndex`：全任务最小的非submitted帧。
- 提交后`nextUnsubmittedFrameIndex`：先取当前之后最小值；没有则回到全任务最小值；全完为NULL。
- C待确认数：固定B版review_changes行数；已决定数为对应decision_heads数量。

平均IoU仅针对修改框。零修改时平均IoU与最大中心位移返回null，前端显示“—”；合法修改的IoU=0或中心位移=0须保留数字0。

## 8. A标注完成、来源汇总与冻结

这一环是现有项目最重要的接入改造：审查页面不能自己用任意前端数组创建A，也不能在接口报错时制造10帧空数据。

### 8.1 预览来源

新增`GET /api/annotation/media/{mediaId}/completion-preview`，仅媒体A编辑者/管理员可调用，返回：

- 真实媒体版本和N/width/height/fps。
- `sourceRevision`：当前可变源文件清单及内容hash形成的摘要。
- 对象帧、明确空帧、未知帧的范围与数量。
- `canComplete`及缺失ID、非法类别/几何、缺失帧等阻断原因。
- 对象预览分页入口；不强制一次返回所有大视频对象。

来源汇总在后端进行：读取已保存workspace_state.json中的人工框、删除/隐藏规则，再读取tracker_results.json。相同(frameIndex,objectId)以人工修正优先，保留A最终接受的AI结果。复用已有前端合并规则并补契约测试，不能把所有AI框丢弃，也不能把显示用warning/anomaly叠加框当成真实对象。

旧seed JSON只作为workspace缺失时的兼容来源。缺失/重复/不合法objectId不自动改成1或数组序号，返回诊断。旧annotations表因按显示名称去重可能混淆同名媒体，只作有可靠mediaId映射的补充，不作为全帧完成的唯一证据。

所有输入均对应原始帧号；不做补帧插值。已有Tracking文件某行存在且明确objects=[]可以作为候选空帧；完全没有该帧记录表示unknown，不能视为空帧。

### 8.2 完成入口

新增`POST /api/annotation/media/{mediaId}/complete`。请求：

```json
{
  "expectedSourceRevision":"sha256:source-example",
  "confirmComplete":true,
  "explicitEmptyFrameRanges":[{"start":8,"end":9}]
}
```

范围0起始，端点均包含。A明确声明未知且确实无对象的帧才使用该字段；不能清空已存在对象的帧，不允许跨出N。已覆盖的空帧可重复声明为无操作。

服务端重新读取/确认同一来源revision，应用A明确的空帧声明，完整校验0…N−1、对象身份、类别、几何，然后在一次DB事务中创建A、全部baseline_frames及唯一pending审查任务。返回201 `{baseline,session}`；同幂等键重试返回原结果。

此动作表示A明确完成已有结果，不增加B的职责。前端必须先完成A工作区保存和Tracking任务，再调用complete。Tracking正在发布/修改本媒体结果时返回409 SOURCE_BUSY，不冻结不稳定来源。

### 8.3 文件与数据库的一致性边界

媒体文件保持不可变；A工作区文件可变。冻结时通过媒体级发布锁取得一致的文件快照与sourceRevision，禁止Tracking/人工写入在此区间修改同一来源。耗时视频hash/解码不放在SQLite写事务里。

SQLite与文件替换不是同一个事务。必须采用统一来源发布协议：可变文件原子替换；冻结前后核对来源清单hash；异常中断后重新扫描源文件生成revision，不能只相信内存计数。若检测到变化，409 SOURCE_REVISION_CONFLICT，整个A冻结不发生。

快照内容一旦写入baseline_frames，读取A只读该快照。后续A工作区变化可产生新基准，不覆盖旧A。

旧`POST /api/review/baselines/freeze`保留为受控兼容入口，v2请求为`mediaId + 同complete字段`，内部调用同一服务。旧`frames`客户端数组冻结方式停止用于正式流程；不得继续让B创建任意不完整A。测试fixture直接调用经过校验的仓储构造器，不绕过生产授权。

## 9. 统一HTTP与权限规则

### 9.1 通用协议

- API前缀继续`/api`；JSON字段统一camelCase，数据库snake_case。响应通过显式Pydantic模型构造，不依赖浅层_camelize猜测嵌套字段。
- 所有业务资源GET/写入需要Bearer JWT，包括baseline、review、confirmation、F、图片与导出下载。
- v2审查写入要求`X-Review-Contract: 2`，缺失或旧版本返回428 CONTRACT_UPGRADE_REQUIRED，防止旧前端沿用自动完成语义。配套前后端同批发布。
- 所有创建/保存/提交/放弃/领取/完成/决定请求要求`Idempotency-Key`；游标PUT可仅用cursor CAS，无需业务幂等表。
- 期望版本用显式字段：expectedFrameRevision、expectedSessionRevision、expectedDecisionRevision、expectedCursorRevision。不得继续把多个含义塞进可选expectedRevision。
- 新建资源201；读取及更新200；同一幂等结果重放保留原状态码和响应，额外响应头`Idempotency-Replayed: true`。
- UTC时间统一ISO8601带Z。金额等无关字段不引入。

### 9.2 最小权限矩阵

采用单工作组默认策略，角色为本设计实施约定。媒体写入/完成由created_by对应A或管理员处理；reviewer可发现有效冻结A并领取；confirmer可发现固定B并领取。读者必须有相关角色或是该任务参与者，不是所有登录用户都能写所有任务。

| 动作 | 权限 |
| --- | --- |
| 上传/编辑A工作区/完成A | annotator且为媒体编辑者，或admin |
| 查看待审查任务、领取 | reviewer；默认不能领取自己提交的A |
| 保存草稿、提交、放弃、完成B | 当前领取B本人；只读任务拒绝写入 |
| 查看C任务、领取 | confirmer；默认与A、B均不同 |
| C决定和finalize | 当前领取C本人 |
| 查看固定A/B/F及相关帧 | 有对应工作组角色或任务参与者 |
| 修改角色、迁移、处理异常旧任务 | admin，通过专门部署/管理流程 |

管理员不得通过常规路由无痕覆盖B/C；若允许代办必须专设审计动作，本期不默认实现。claim冲突返回409 SESSION_ALREADY_CLAIMED；无角色/非领取人写入返回403。sessionId与frameId/changeId不匹配返回404，避免跨资源操作。

不将“前端按钮隐藏”“调用者知道ID”“拥有JWT”当成完整授权。

### 9.3 错误格式

```json
{
  "code":"FRAME_REVISION_CONFLICT",
  "message":"本帧已在其他窗口更新，请重新加载后处理当前编辑。",
  "details":{"sessionId":"rs_example","frameIndex":189,"expectedRevision":4,"actualRevision":5},
  "requestId":"req_example"
}
```

| HTTP | code示例 | 客户端动作 |
| --- | --- | --- |
| 401 | AUTH_REQUIRED / AUTH_EXPIRED | 重新登录，保留未同步编辑 |
| 403 | FORBIDDEN / NOT_ASSIGNEE / ROLE_SEPARATION_REQUIRED | 提示权限问题，不重试写入 |
| 404 | SESSION_NOT_FOUND / FRAME_NOT_FOUND / CHANGE_NOT_FOUND | 停止当前资源操作 |
| 409 | FRAME_REVISION_CONFLICT / SESSION_REVISION_CONFLICT / DECISION_REVISION_CONFLICT | 获取新版本，保留本地修改，不自动覆盖 |
| 409 | IDEMPOTENCY_KEY_REUSED | 新逻辑操作用新key；原重试保持同key |
| 409 | SESSION_READ_ONLY / FRAMES_NOT_SUBMITTED / DECISIONS_PENDING | 根据状态返回相应流程 |
| 409 | SOURCE_BUSY / SOURCE_REVISION_CONFLICT / LEGACY_TASK_READ_ONLY | 刷新来源或处理迁移，不创建假数据 |
| 422 | INVALID_BBOX / UNKNOWN_OBJECT / DUPLICATE_OBJECT / INCOMPLETE_COVERAGE / INVALID_FRAME_INDEX | 指明字段/对象/缺失帧，修正请求 |
| 428 | CONTRACT_UPGRADE_REQUIRED / IDEMPOTENCY_KEY_REQUIRED | 升级客户端或补必要头 |
| 503 | STORAGE_UNAVAILABLE / DATABASE_BUSY | 保持编辑，用原key重试；可带Retry-After |
| 500 | INTERNAL_ERROR | 记录requestId，不暴露SQL或服务器路径 |

缺少必填请求体字段走统一422校验。FastAPI默认验证错误需转换为上述格式；现有http.ts增加code/details/requestId，不再只保留message/status。

### 10.1 列表与详情

列表统一`limit`（默认20，最大100）、`offset`、稳定排序`createdAt DESC,id DESC`；响应`items,total,limit,offset`。视频列表支持`q,state,mediaId`。可见集合先授权再筛选，statusCounts使用同一q/mediaId范围但不受当前state选项限制。任务详情不再附带所有帧patch，避免大视频一次全量加载。

示例`GET /api/review/sessions/rs_example`：

```json
{
  "id":"rs_example",
  "contractVersion":2,
  "baselineId":"abl_example",
  "state":"in_progress",
  "revision":17,
  "reviewerId":2,
  "media":{"mediaId":"T20x_001","mediaRevisionId":"mrev_example","name":"T20x_001.avi","width":1920,"height":1080,"frameCount":1000,"fps":30},
  "progress":{"submittedFrames":189,"unsubmittedFrames":811,"draftFrames":1,"modifiedFrames":56,"modifiedBoxes":72,"percent":18.9},
  "resume":{"lastViewedFrameIndex":189,"firstUnsubmittedFrameIndex":189,"draftFrameIndexes":[189],"draftFramesTruncated":false},
  "permissions":{"canClaim":false,"canEdit":true,"canComplete":false},
  "completedReviewVersionId":null

```

draftFrameIndexes最多返100条，超出给truncated=true并通过帧状态分页获取。completed任务的建议浏览位置为该用户有效游标或第0帧，不把它伪装成“继续未完成审查”。

### 10.3 保存草稿

`PUT .../frames/189/draft`：

```json
{
  "expectedFrameRevision":4,
  "patch":[{"objectId":4,"bbox":[520,338,546,364]}]
}
```

`patch`必填，即使为空数组；不设置默认空数组，否则遗漏字段会被误认为恢复全部A。它是全帧当前稀疏差量替换，不是仅对最后一个框的增量合并。

服务端校验、标准化并删除与A完全相同的元素后，比较最近成功提交的有效几何。确有新编辑时写draft并令state=unreviewed；恢复到成功提交时删除draft并恢复submitted。未发生有效变化则不新增版本。

响应200：`frame`（最新单帧状态/草稿/版本）、`sessionRevision`、`progress`、`savedAt`。不返回“submitted=true”，不跳帧，不覆盖上一成功提交。保存后前端采用返回的标准化几何。

### 10.4 放弃草稿

`POST .../frames/189/discard`：

```json
{"expectedFrameRevision":5}
```

有最后成功提交S1：删除draft、恢复state=submitted、submission_id保持S1；没有成功提交：删除draft、state=unreviewed、有效结果A。没有draft时幂等返回当前状态，不减少进度。响应与草稿写入相同，并含`discarded=true|false`。

放弃失败，数据库原草稿和旧状态都保留；客户端不能先永久清空自己的编辑再等待服务端结果。

### 10.5 提交本帧

`POST .../frames/189/submit`：

```json
{
  "expectedFrameRevision":5,
  "patch":[{"objectId":4,"bbox":[520,338,546,364]}]
}
```

提交携带点击时完整有效patch，不能让服务端猜测最新草稿请求是否已经抵达。前端同帧请求串行化，服务端仍用revision防止迟到覆盖。

  "frameIndex":189,
  "submissionId":"sub_example",
  "frameRevision":6,
  "sessionRevision":19,

没有修改或空帧发送patch=[]同样创建提交记录。已经submitted且请求内容等于当前成功提交时，返回alreadySubmitted=true和原submissionId，禁止再增加历史记录。提交接口不返回autoFrozen，也不创建C任务。

### 10.7 游标

GET `/api/review/cursors?stage=review&sessionId=rs_example`返回：

```json
{"cursor":{"stage":"review","sessionId":"rs_example","frameIndex":189,"changeId":null,"revision":3,"updatedAt":"2026-09-26T12:00:00Z"}}
```

无记录返回cursor=null，写入expectedCursorRevision=0。PUT请求：

```json
{"stage":"review","sessionId":"rs_example","frameIndex":191,"changeId":null,"expectedCursorRevision":3}
```

验证范围/归属和当前用户权限，成功revision+1。多个页面以cursor CAS防乱序；冲突后只有最新实际浏览意图才重新发起，不能用旧请求覆盖新位置。恢复提示读取历史cursor再选择目标；后续新浏览才写回，不让渲染函数提前覆写“上次位置”。
